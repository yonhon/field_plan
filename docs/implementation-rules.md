# 実装のきまり

処理を書くとき、直すときに守るきまりです。画面の見た目のきまりは `docs/design-rules.md` にあります。

## 待つこと

- **確認の窓や保存を待つ関数は、呼び出す側も `await` する。** `confirmAction` や `confirmDelete` は、利用者が答えるまで終わらない。呼び出したあとの処理は、待たないと答えの前に走る。
- **同期の関数を async に変えたら、呼び出す側をすべて直す。** 呼び出す関数が Promise を返さないと、その先は待てない。包むだけの関数でも `return` する。
- **図は、データを変え終えてから描き直す。** `render` は圃場図と右の欄だけを描く。日程の画面を変えたら `renderSchedule` も呼ぶ。

## 保存の順序

- **親の行を、子の行より先に送る。** 区域 → 区画 → 畝 → 作付 → 作業の順に外部キーがあり、子が先に届くと 23503 で断られる。毎回は起きないので、動かして見ただけでは気づけない。
- **DB への書き込みは `state.store` を通す。** `inOrder` が呼んだ順に 1 つずつ送るので、親を先に呼べば順序は守られる。
- **`queueSave` は、すぐには送らない。** 600 ms あとに送る。`queueSave` した行を親にする行を保存するときは、先に `sendPendingSaves` を待つ。
- **画面の中の値が変わったことは、保存が終わったことを意味しない。** 保存のあとに続く処理は、その完了を待つ。
- **DB への書き込みの関数を足したら、`QUEUED_WRITES` にも足す。** 送る順序と、操作の ID（`op_id`）は、ここで決まる。

## 失敗の知らせ方

- **保存の失敗は、窓で知らせる。** ヘッダーの下のお知らせは、ほかの保存が終わると置き換わったり消えたりする。`persist` と `run` は失敗すると `notifySaveFailed` を呼ぶので、これらを通して保存する。
- **保存の状態の文字は `setStatus` で出す。** 送り残しがあるあいだは「保存しました」と書かず、もう一度送る。書いた文は、目に見えない記録の欄（`#saveStatus`）に入り、`app/toast.js` がヘッダーの下のお知らせに出す。失敗は「…に失敗しました: 誤りの内容」「…ませんでした: 誤りの内容」の形で書く（この形のものだけが、閉じるまで残るお知らせになる）。
- **失敗を捨てない。** `catch` したら、利用者に見える形で知らせる。

## 元に戻す

- **元に戻すは、書き込みの操作の ID で戻す。** `history.js` は、書き込み（`store.js` の `upsert`、`remove`、`saveField`、`saveLog`、`deleteLog`、`saveWorkType`、`saveBackdrop`、`saveFieldWeather` と、プランの操作の `createPlan`、`copyPlan`、`renamePlan`、`deletePlan`、`setActivePlan`。一覧は `history.js` の `UNDOABLE_WRITES`）を列に入れたときの操作の ID を積み、DB の関数 `field.undo_op` で、その ID の変更を DB の側で戻して、返った行を画面に当てる（`app.js` の `applyUndo`）。新しい操作も、この書き込みを通せば、元に戻すを書かなくてよい。
- **書き込みは、操作の中で送る。** 操作の ID は、押す・キーを打つの始まりで作る。押したあとに `await` をはさんで書くと、そのあいだに次の操作が始まり、別の操作の ID で記録される。保存の予約（`queueSave`）と書き込みの列（`inOrder`）は、予約した時点の ID で送るので、それを使う。
- **表を足したら、元に戻すの 4 か所を見る。** 1 から 3 の足し忘れは `tests/undo-tables.test.mjs` が見つける。4 はテストでは見つからない。
  1. `field.undo_op` の表の順（`v_order`。親から子）。
  2. `history.js` の `UNDO_APPLY`（画面への当て方。当て方を決めないなら `UNDO_NOT_APPLIED`）と、`app.js` の `applyUndo`。`applyUndo` に当て方のない表の行が返ると、DB から読み直して履歴を空にする。
  3. このブラウザーの保存の変更の記録（`store.js` の `AUDITED`）。
  4. 戻した行を選んで光らせる処理（`app.js` の `showUndone`）。行を、画面の要素の `data-` の属性（`data-shape`、`data-bed`、`data-planting`、`.gantt-bar` と `.pe-card` の `data-id`、`td.detail-plan` の `data-plan`、`data-log` など）で探すので、表や、行を出す画面を足したら、ここにも足す。
- **戻せない操作は、行ったあとに `resetHistory()` を呼ぶ。** その操作の ID は、このあと書いても履歴に積まない。
- **プランによらない操作は、圃場の操作にする。** 履歴の 1 回ぶんは、操作したときに開いていたプランを覚え、別のプランを開いているときは戻さない。プランの操作（`createPlan` など）は自動で圃場の操作になる。何回かに分けて書く圃場の操作（圃場の設定の窓の保存）は、書く前に `markSettingsOperation()` を呼び、書き込みを `bindOperation` で同じ操作の ID に束ねる。プランの操作と圃場の設定の保存は、戻す・やり直すときに、その窓を開いてから戻す（`ctx.showDialog`）。
- **窓の中で DB に書く操作を足したら、戻すときにその窓を開き直すかを決める。** 1 回ぶんは、操作をした画面（URL のハッシュ）を覚え、戻す・やり直すときはその画面に移る。窓は URL を変えないので、ふだんは窓の後ろの画面に移るだけになる。開き直すのは、いまは「圃場とプラン」の窓と圃場の設定の窓だけ（`history.js` の `dialog`、`app.js` の `showDialog`）。
- **戻せない操作は、README の「元に戻す、やり直す」に書く。**

## DB の形を変える、部品を足す

画面は、アプリのファイルを一式ブラウザーに取っておき（`app/sw.js`）、起動のときはそこから出す。新しい版に切り替わるのは、お知らせの「読み込み直す」を押すか、次に開いたとき。そのため、公開してからしばらくは、古い版の画面が DB に書く。

- **古い版の画面では正しく書けない形に DB を変えるときは、古い版を止める。** 列の名前を変える、必須の列を足す、書き込みの決まりを変える、などのとき。次の順に行う。
  1. `app/store.js` の `APP_VERSION` を 1 つ上げ、DB の変更に合わせた画面を公開する。
  2. 開いたままの画面を閉じておく。起動のときにしか確かめないので、開いたままの画面は止まらない。
  3. 公開を待ってから、DB を変える SQL の中で、`field.app_compat` の `min_version` を同じ値に上げる（`update field.app_compat set min_version = 2;`）。

  `min_version` より古い画面は、起動のとき、データを出す前に止まって、新しい版を読み込み直す。順序を逆にすると、新しい版がまだないので止まったままになる。
- **古い版の画面でも壊れない変え方ができるなら、そうする。** 列を足すだけなら、古い版は新しい列を知らないまま動ける。先に列を足し、両方の版が動くようにしてから、古い列を消す。
- **`field` スキーマに表を足したら、`sql/field.sql` の方針（policy）の一覧に足す。** `field.sql` は、まず `authenticated` にすべての表の読み書きを許し、そのあとで一覧の表に方針を付ける。足し忘れた表は、RLS だけが付いてだれも読み書きできず、`field.sql` の最後の確かめが失敗する。画面から読み書きしない表は、確かめの「方針がなくてよい表」に足す。
- **方針（policy）の条件で `field.is_owner()` や `field.is_importer()` を呼ぶときは、`(select field.is_owner())` のように `select` で囲む。** 囲まないと、読む行ごとに関数を呼ぶ。囲むと、問い合わせ 1 回につき 1 度だけ評価する（2026-11-15 の測定で、作業 450 行の読み込みが 6.7 ms から 0.4 ms になった）。囲んでいない方針があると、`field.sql` の最後の確かめが失敗する。
- **`field` スキーマに表を足したら、操作の記録（`audit_log`）の対象にするかを決め、`sql/field.sql` の 2 つの一覧のどちらかに足す。** 計画や実績のように、画面が読み書きし、ほかの端末の変更を拾う必要がある表は、トリガー（`write_audit_log`）を付ける一覧に足す。管理用の表や外から取り込む表は、最後の確かめの「対象にしない表」に足す。どちらにもない表があると、`field.sql` の最後の確かめが失敗する。
- **起動、戻ってきたときの読み直し、圃場の切り替えで読む中身は、DB の関数 `field.load_field`（`sql/field.sql`）と、`app/store.js` の `composeLoadField` の 2 か所で決まる。表を足す、読む行の絞り方や並び順を変えるときは、両方を直す。** 表は行ごと返すので、列を足すだけなら直さなくてよい。`composeLoadField` は `?local=1` の店と、DB の関数がないときに使う。
  - `tests/load-field.test.mjs` が、2 か所の読む表の食い違いを確かめる。`composeLoadField` に読み込みを足したら、テストの `LOADERS` にも足す。
  - 読む表は、`audit_log` の対象にする。画面は、DB の変更の印（`audit_log` の最後の番号）が前に読んだときと同じなら読み直さない。トリガーのない表の変更は番号を進めないので、ほかの端末で変えても拾えない。`tests/audit.test.mjs` が確かめる。
  - 通しテストは `composeLoadField` しか通らない。`load_field` を直したら、本番の DB に直接つないで、本人の権限で呼び、表ごとに読んだ結果（並び順を含む）と同じになるかを確かめる。
- **端末に取っておく圃場の中身（`app/field-cache.js`）は、DB から読んだそのままの中身と、そのときの DB の変更の印だけにする。画面の `state` を取っておかない。** 起動のときは、印が同じなら、取っておいた中身を DB の中身として使う。画面で変えたが保存できなかった中身を取っておくと、それが DB の中身として出てしまう。取っておくのは `store.loadField` の返事で、写しは呼んだ時点で取る（`writeFieldCache`）。取っておく形を変えたら `FORMAT` を上げる。アプリの版（`APP_VERSION`）が違う中身は使わない。日記は取っておかない。ログアウトで消す。
- **DB の中身を写したデータ（`state` の表）は、書き込みを送らずに変えない。** 戻ってきたときの読み直しは、どこからも書き込みがなければ DB と比べない。書き込みを伴わずに画面だけを変えると、そのずれは直らずに残る。書き込みが失敗したときは、`inOrder` が失敗の数を数え、次に戻ったときに読み直す。
- **JS の部品（ファイル）を足したら、`app/sw.js` の `FILES` と、`app/boot.js` の `parts` の両方に足す。** 漏れると、その部品だけが一式から外れ、古い版と新しい版が混ざる。`tests/sw.test.mjs` が漏れを確かめる。
- **版の印（`app/version.json`）は、公開の手順（`scripts/build-version.mjs`）が、公開するファイルそのものから作る。手で作らない。コミットしない（`.gitignore` で除いてある）。** `FILES` を変えても、版の印は自動で追う。Service Worker は、版の印で版が変わったかを確かめ、取ったファイルを版の印のハッシュと照らし合わせてから入れ替える（公開の直後に新旧のファイルが混ざって届いても、混ざった一式で動かない）。公開のあとに、公開中のサイトの中身が版の印と同じかを、Actions が確かめる。
- **画面が読むファイル（アイコンなど）を足したときも、`FILES` に足す。**
- **スクリプトは、ファイルに書く。HTML の中には書かない。** `index.html` の Content-Security-Policy が、このサイトのファイルのスクリプトだけを動かす。`<script>` の中のコード、`onclick` などの属性、`javascript:` のリンクは動かない。`tests/sw.test.mjs` が確かめる。
- **HTML に入れる文字は、`app/html.js` の `escapeHtml` を通す。** 部品ごとに同じものを書かない（前は 17 か所に写しがあり、1 つだけ中身が違っていた）。
- **`sql/field.sql` は、空の DB でも最後まで流れる順に書く。** 表を作る前にその表を書き換えない。`language sql` の関数は、作るときに中身を確かめるので、使う列を足したあとに置く。直したら `scripts/check_field_sql.py` で確かめる（README の 12 章）。
- **スクリプトは、外のサーバーから読まない。** 外のライブラリーは、版を決めたファイルを `app/vendor/` に置き、`FILES` に足す。外から読むと、アプリを変えなくても中身が変わり、一式からも外れ、届かないと起動できない。`tests/sw.test.mjs` が確かめる。版の上げ方は README の 12 章。

## 画面を描く

画面は、入れ物の中身を HTML の文字列で丸ごと作り直して描く。作り直すと、スクロールの位置とカーソルが失われるので、`app/draw.js` の `draw` を通して描く。`draw` は、作り直す前に、触っていた所の高さ、スクロールの位置、カーソルのある欄を覚え、作り直したあとに戻す。

将来、違う所だけを書き換える仕組み（idiomorph など）に替えるときは、`draw` の中身だけを替える。替えると、作り直さずに前の要素を残して使うようになる。そのときに直す所が出ないよう、次のきまりを守る。

- **中身を入れ替えるときは `draw(入れ物, html)` を使う。`innerHTML`、`outerHTML`、`insertAdjacentHTML` を直接使わない。** 直接使うと、スクロールの位置とカーソルが失われる。`tests/draw.test.mjs` が確かめる。中身を空にするだけなら `replaceChildren()` でよい。
- **画面の状態は、データに持つ。描いた要素から読み戻さない。** チェック、選んだもの、開いている欄、入れかけの文字などは、操作のたびにデータ（`draft` など）へ入れ、描くときはデータから HTML を作る。要素に残った状態は、作り直すと消え、前の要素を残す仕組みでは前の値が残る。どちらでも同じに見えるのは、データから描いたときだけ。
- **HTML で書けない状態（`indeterminate` など）は、描くたびに、データから付け直す。** `draw` のすぐあとに付ける。前に付けた値が残っていることを当てにしない。
- **操作の処理は、入れ物か、その外の要素に付ける。描いた中身の要素には付けない。** 中身の要素に付けると、作り直す仕組みでは描くたびに消え、前の要素を残す仕組みでは描くたびに重なる。入れ物に付け、`event.target.closest(…)` でどの要素かを見分ける（`crops-view.js` の `bind`）。
- **描いた中身の要素を、描き直しのあとまで持ち続けない。** 描き直したあとは、`querySelector` で探し直す。作り直すと前の要素は画面から外れ、前の要素を残す仕組みでは同じ要素が別の中身になる。
- **入力欄、ボタン、行には、`data-*` か `id` で、どれかが分かる印を付ける。** `draw` は、この印で、作り直したあとの同じ要素を探す（行の `data-id` と欄の `data-field` を合わせて、「どの行のどの欄」かを決める）。印のない要素には、カーソルを戻せない。違う所だけを書き換える仕組みも、この印で同じ要素を見分ける。
- **欄を描く処理を、いまどの画面を出しているかで止めない。** 窓は、どの画面からも開く。圃場の設定の窓の気象の欄は、圃場図が隠れているときに描くのを止めていたため、日程の画面から窓を開くと、起動したときの欄が残っていた（2026-11-17）。止めてよいのは、描くためのデータがまだないとき（圃場を読む前など）だけ。
- **作り直したことで、元に戻ることを当てにしない。** 入れかけの文字を消す、スクロールをいちばん上にする、などは、その処理を書く。前の要素を残す仕組みでは、作り直さないので戻らない。窓を閉じたあとに中身を空にする（`log-view.js`）のも、このため。
- **JS でスクロールの位置（`scrollTop`、`scrollLeft`）を変えたら、`draw.js` の `noteScroll(要素)` を呼ぶ。** `draw` は、描き直す前に、スクロールしている要素の位置を覚えて戻す。どの要素がスクロールしているかは、スクロールの知らせで覚える。描くたびにすべての要素の位置を読むと、そのたびにブラウザーがページ全体の配置を計算し直して重いので、そうしていない（工程表の中は数千の要素がある）。スクロールの知らせは少し遅れて届くので、位置を変えた直後に同じ処理の中で描き直すと、`noteScroll` を呼ばない限り、その位置を取りこぼす。
- **`draw` の中に、要素の寸法や位置を読む処理を足さない。** 描き直しのたびに、ページ全体の配置の計算を起こす。描く前に読む必要があるものは、読む回数が増えないように、呼ぶ側でまとめて読む。
- **文字を打つたびに（`input` の知らせで）、その欄を含む入れ物を描き直さない。** 日本語の変換の途中で作り直すと、変換が切れる。打つたびに変える所（検索の結果など）は、別の入れ物にして、そこだけを描く。

- **SVG の文字の一部だけを押せるようにするときは、`tspan` に分けず、押した位置から文字を求める。** WebKit（iPad、iPhone の Safari と Chrome）では、`tspan` に分けると、`dominant-baseline` が効かずにその部分だけ高さがずれ、`pointer-events` も効かず下の図形が押される。PC の Chrome ではどちらも起きないので、通しテストでは気づけない。圃場図の品目名は、文字を 1 つのまま、`getExtentOfChar` で押した位置が品目名の文字の範囲かを求めている（`app.js` の `mapLabelAt`）。文字が図形からはみ出すときは、図形をすべて描いたあとに文字を描く（先に描くと、隣の図形に隠れる）。

## 確かめ方

- **操作の流れを変えたら、ブラウザーの通しテストを動かす。** 計算のテストは、画面の操作のバグを見つけられない。主な操作を足したら、`tests/e2e/` にテストを足す。
- **画面に戻ってきたときに通信するものは、`app-returned` の知らせで行う。** `app.js` が、60 秒以上隠れていたあとに戻ってきたときだけ、この知らせを出す（圃場の中身の読み直し、ニュースの読み直し、アプリの更新の確かめ）。`visibilitychange` を自分で受けて通信すると、アプリを数秒行き来するたびに携帯の回線を起こす。
- **大きな機能を足したら、`node scripts/perf/run.mjs` で画面の速さを測り、`docs/perf-runs.md` の前回の記録と比べる。** 続け方と、レビューに進む目安は `docs/performance.md` にある。1 月と 7 月には、Actions が定期の確かめの Issue を開く。
- **計算のファイルを直したら、コミットの前に `node mutation/run.mjs --since HEAD` で、計算のテストが誤りに気づくかを確かめる。** 対象は `mutation/mutator.config.json` の `include` のファイルで、コミットしていない変更の所だけを回す。直した所に Survived が出たらテストを足し、NoCoverage が出たら、その所を通るテストを足す。どう書き換えても結果が変わらないものは、`node mutation/run.mjs accept <key> --reason "理由"` で記録してコミットする（等価だと言い切れないものは記録しない）。農薬の使用回数、使用基準、量、指摘にかかわる関数には `// mutator-critical` を付け、終了コード 2（その関数の中に、記録していない気づかない変異がある）のままではコミットしない。計算の不具合を直してテストを足したときも同じ。mutator の版を上げたときと、1 月と 7 月の定期の確かめでは、全体を回して `docs/mutation-runs.md` に足す（README の 12 章）。
- **保存に関わる変更は、`?local=1&strict=1` で動かす。** 親の表ほど保存を遅くし、親のない行を断る。ふつうの `?local=1` は保存がすぐ終わるので、順序の誤りが出ない。
