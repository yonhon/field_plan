# 設計の判断

なぜそう作ったかの記録です。いまの動きは [使い方](manual/README.md) とコードにあります。ここには、コードからも使い方からも読み取れない、判断とその理由だけを書きます。同じ案をもう一度出す前に、ここを見ます。

作業の実績、農薬、気象、農作業日記を作ったときの元の計画（`docs/actuals-plan.md`）は、2026-11-27 に消しました。全文は Git の履歴にあります（`git show 7cd8374:docs/actuals-plan.md`）。

## 作業の実績

- **実績は、計画とは別の表に持つ。** 計画の作業に実施日を入れるだけでは足りなかった。手で付けていた記録には、計画にない作業（灌水、発芽確認、除草、防除など）が多く、1 つの作業が日をまたいで日ごとに中身が違い、資材や実際の仕様（株間、条数など）もあった。
- **実績は圃場に付け、計画の畝・作付・作業へは「つながり」として持つ。** プランは配置の案を比べるもので、コピーも削除もされる。実績は事実なので、案と一緒に消えてはいけない。つながりの先が消えても、実績は記録した時点の名前（例: 「区画 A 畝 3 キャベツ」）で読める。
- **実績をつなぐプランは、圃場ごとに 1 つ（実際に使うプラン）。** 実績の単位は畝（作付）で、入力では品目でまとめて選べるようにした。
- **実績をどの計画につなぐかは、どこから入力したかで決める。アプリは推測してつながない。** 計画の「完了」「修正」から入れた実績だけをその計画につなぐ。初めは「同じ種類で、まだ終わっていない最初の計画」に自動でつないでいたが、防除のように繰り返す作業で、計画にない臨時の防除が来週の防除の計画を「完了」にしてしまったので改めた。
- **計画は自動では動かさない。** 実績が計画とずれても、勝手に書き換えると元の計画が分からなくなる。後ろをずらすのは「実績に合わせて後ろを並べ直す」を押したときだけ。
- **「未実施」は実績がない状態で、やらないことにした作業には「取りやめ」の印を付ける。** 手で付けていた記録では、「未実施」と「その品目にはない作業」を区別できなかった。
- **言葉**: 農薬を使う作業は「防除」。作業には「計画」と「実績」があり、入れることを「入力」と呼ぶ。「記録」は、DB の表の名前（`work_logs`）など、内部の名前にだけ残す。

## 農薬

- **品目と FAMIC の作物名の対応は、前もって決めない。防除を入力するときに、本人が選ぶ。** FAMIC の作物名には、品目の名前のほかに「野菜類」「ねぎ類」のようなまとめた名前があり、その中身（「野菜類(…を除く)」など）は農薬ごとに違う。
- **当てはめが正しいかは、アプリは判定しない。** 判定すると、指摘が出ないことを「正しい」の印と受け取られる。窓には、当てはめは本人の判断で、使う前にラベルで確かめるよう書く。
- **登録番号のある農薬は、作物名と使い方を選ばないと保存できない。「該当なし」は選べない。** 当てはまる作物名のない農薬は使えない。名前だけで入れる農薬（登録番号なし）は保存できる。
- **有効成分の総使用回数は、登録基本部の「総使用回数における有効成分」の列で数える。** 「有効成分」の列とは違うことがある。育苗中の防除は、定植する予定の作付に付けて、同じ作付に数える。
- **使用基準を外れても、指摘するだけで保存は止めない。** 希釈が薄い、量が少ないなど、基準より控えめな側は指摘しない。
- **FAMIC の取り込みは、列の名前や数が前と違えば取り込まずに失敗させる。** 形式が変わったときに、黙って壊れた値を入れないため。
- **使用基準の部分は、切り離せるように作る。** 農薬の情報の扱いには責任が伴う。外しても（`app/config.js` の `famic`）、防除は名前と量を文字と数で入れられる。
- **GitHub Actions の取り込みは、専用の利用者（取り込み係）でログインして行い、DB の接続文字列は GitHub に置かない。** 接続文字列は RLS を通らず、共用の DB のすべての表を読み書きできる。取り込み係なら、漏れても触られるのは気象、FAMIC、ニュースの表だけ。
- **農薬名の後ろには、必ず作用機構分類（RAC コード）のアイコンを付ける。** 同じ作用機構の農薬を続けて使わない（ローテーション防除）目安にするため。形と色は、現代農業 2018 年 6 月号「RAC コードでローテーション防除」の表にならった（HRAC は表にないので、作用機構のまとまりで色を決めた）。

## 気象

- **気温と降水量は、気象庁のアメダスから取る。** 衛星の地表面温度（JAXA の GCOM-C など）は使わない。地面そのものの温度で、積算温度に使う気温（地上 1.5 m ほど）とは違い、晴れた日中の裸地やマルチでは 10 ℃ 以上高くなる。雲の下は値が欠け、衛星が通る時刻の値なので日平均にならず、格子（4〜5 km）も圃場より大きい。
- **正式な値（過去の気象データの日別の表）を優先し、サイトの表示用の JSON は予備にする。** JSON は 11 日前までしか残らず、ときどき値が抜け、最高・最低気温も 10 分ごとの値から選ぶので控えめになる。日別の表はブラウザーから読めない（CORS）ので、GitHub Actions が読む。
- **気温の観測所と雨量の観測所は、圃場ごとに別々に選ぶ。** 気温を測る観測所は、雨量だけの観測所より少ない。
- **欠測の日は、ほかの観測所の値で埋めない。** 積算に穴が開いたことを画面に出す。
- **予報は DB に持たず、作付の詳細を開いたときに読む。**

## 農作業日記と写真

- **日記は、Google ドキュメントではなくこのアプリで書く（2026-11-07 に切り替えた）。** 1 つのファイルが長くなってスマホで書き足すのが大変で、書いたあと DB への取り込みを別に行う必要があった。
- **正本は 1 日 1 行の Markdown。見出しごとの節は、保存のたびに作り直す。** diary-mcp が読む節の形は変えない。
- **日記を守る仕組みは、`inoo_farm` のまま変えない。** 日記にはほかの方の氏名や連絡先が入る。`diary` スキーマは API に出さず、画面からは本人だけが通れる関数を通して読み書きする。本物の日記は、テストにも画面の見本にも使わない。
- **写真は 1 種類だけ（短辺 1080 px、品質 85 の JPEG）。元の写真は保存しない。** Instagram の横幅に足り、SNS にそのまま使える。SNS は投稿をもう一度圧縮するので、品質は前の縮小版（78）より上げた。1 枚およそ 0.25 MB で、Supabase の無料の枠に数年分入る。元の写真はスマホと Google フォトに残るので、撮影日時と元のファイル名で探す。
- **写真は、カメラのアプリで撮ってアルバムから選ぶ。** ブラウザーから直接撮ると、アルバムに残らず、Google フォトにも上がらないことがある。
- **Google フォトに置いたまま、このアプリから見る形は採らない。** 2025 年 3 月から、外部のアプリは Google フォトにもともとある写真を読めなくなり、選んで受け取った写真の URL も 60 分ほどで切れる。
- **写真のバックアップは、DB の世代ごとのバックアップに載せず、新しい写真だけを 1 回写す。** 丸ごと取ると、同じ写真が 30 世代ほど重なって残る。写真は一度上げたら中身が変わらない。
- **容量（Storage 1 GB）に近づいたら、有料のプランに上げるか、写真を R2 に移すかを、そのときに選ぶ。** R2 に移すときは、使う場所とバックアップがどちらも Cloudflare になるので、バックアップの置き場所を分け直す。
- **写真は日記に付け、作業の実績（メモ欄）には付けない（2026-11-09）。** 作業と写真は、日記の対象の一覧で並べて見る。日記の写真には、大きさ、Google フォトで元を探す手がかり、写真のタグ、バックアップ、diary-mcp での写真選びがそろっていて、実績にも持たせると二重に作ることになる。2 か所に付けられると、探すときに両方を見ることになる。実績は、集計に使う決まった形のまま保つ。
- **タグは、保存のときに語で自動に付けず、本人が頼んだときに Claude Code が本文の意味と写真の中身から付ける（2026-11-08）。** 語が含まれていれば付ける形は、決まった語で本文を検索した結果と同じで、検索で足りる。一覧にない作物には付かず、部分一致で違う意味の語にも付く（「ナス科」でナス、など）。
- **小見出しのあとで、親の見出しの位置の文に戻る書き方は作らない（2026-11-10）。** Markdown にその書き方がなく、`---`（区切り線）は見た目で大きな区切りに見える。親の位置に書くことは小見出しより前に書き、後に書くことは「### まとめ」のような小見出しにする。
