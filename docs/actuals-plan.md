# 作業の記録（計画）

README の「作る順番」の 5 番目の計画です。まだ実装していません。
農作業日記をこのアプリで書く計画と、日記と記録の突き合わせ（いまは取り組まない）、記録の写真の扱い（日記に付け、記録には付けない）は、最後の 11 章にまとめています。

## 1. ねらい

- 実際に行った作業を、日付、対象の畝、内容、使った資材とともに記録する。
- 計画の作業に記録を結びつけて、計画と実績のずれを見て、後ろの計画を直せるようにする。
- 農薬の使用回数（同じ成分を何回使ったか）を、作付ごとに確かめられるようにする。
- 定植・播種からの積算温度と積算降水量と、これからの予報を出す。

## 2. 前提

### 2.1 これまで手で付けていた作業の記録から分かること

これまでは、作業の記録を表計算の表で付けていました。行が品目、列が作業の種類（畦立て・マルチ、育苗播種、作付、発芽確認、灌水、除草、防除、積算温度・積算降水量、備考）、マスが日付です。そこから、次のことが分かります。

| 見えたこと | 例 | 計画のテーブルでは |
|---|---|---|
| 計画にない作業が多い | 灌水、発芽確認、除草、防除、防風ネットの設置、育苗の播種 | `work_types` にない。灌水のように何度も繰り返す作業は、計画の作業 1 件に日付 1 組では収まらない |
| 1 つの作業が複数の日にまたがり、日ごとに内容が違う | 1 日目は畦立て、2 日目は畦立てとマルチ。定植が 2 日がかり | 開始と終了の 2 つだけでは、日ごとの内容を残せない |
| 資材の記録 | 植付の前日に種球を薬剤に浸漬。定植時に粒剤を土壌混和 | 置く場所がない |
| 実際の仕様 | 株間、条間、条数、植える深さ、マルチ穴の大きさ、実畦と通路の幅 | 作付の値は計画の上書きで、実績とは別のもの |
| 状態 | 「未実施」と「－」（その品目にはない作業） | 区別できない |
| 記録はまとめて付ける | 行は品目ごと。同じ品目でも、裸地とマルチ畦のように作り方が違えば行を分ける | 作業は作付（畝 1 本）ごと |
| 積算温度・積算降水量 | 列だけあって、空欄 | 記録ではなく、気象データから計算する値 |

`field.works` の `actual_start` と `actual_end` に日付を入れるだけでは、これらは残せません。そのため、記録は計画とは別のテーブルで持ちます。

### 2.2 記録を計画から切り離す理由

プランは、配置の案を比べるためのものです。コピーも削除もされ、削除すると中の作業も一緒に消えます。記録は事実なので、案と一緒に消えてはいけません。

そこで、記録は圃場に付け、計画の畝・作付・作業へは「つながり」として持ちます。つながりの先が消えても記録は残り、記録した時点の名前（例: 「区画 A 畝 3 キャベツ」）で読めます。`field.changes` が、その時点の名前で文を残すのと同じ考え方です。

## 3. 決めたこと

| 項目 | 決めたこと |
|---|---|
| 記録の単位 | 畝（作付）ごとに持つ。入力は品目でまとめて選べるようにする |
| 記録をつなぐプラン | 圃場ごとに「実際に使うプラン」を 1 つ決め、記録はそのプランの畝・作付・作業につなぐ |
| 資材の細かさ | 農薬は、名前、量、使い方に加えて、希釈倍率、散布量を記録し、使用回数（製品ごとと、有効成分ごと）を確かめる |
| 農薬の使用基準 | FAMIC が配布する農薬登録情報の CSV を DB に持ち、定期的に更新を確かめて取り込む。この部分は切り離せるように作る（4.7） |
| 気象データ | 気温はアメダス。雨量はアメダスで、雨量計が遠ければ GSMaP で補う。圃場の温度ロガーは任意。予報は気象庁で取れる範囲だけ |
| 振り返りの画面 | 新しいタブは作らず、日程の工程表に「計画／実績／計画と実績」の切り替えを足し、作付の詳細の画面を作る |
| 用語 | 農薬を使う作業は「防除」と呼ぶ。作業には「計画」と「実績」があり、計画や実績を入れることを「入力」と呼ぶ（画面の言葉もこれにそろえる。計画の変更の履歴は「履歴」）。「記録」は、DB の表の名前（`work_logs`）など、内部の名前にだけ残る |
| 農作業日記 | このアプリで書けるようにする（11.1）。記録との突き合わせは、いまは取り組まない（11.2）。写真は日記に付け、記録には付けない（11.3） |

## 4. テーブル

すべて `field` スキーマに置き、ほかのテーブルと同じく `field.owners` の利用者にだけ読み書きを許します。行を変えるたびに `field.audit_log` に残すトリガーも付けます。

```
fields
├─ active_plan_id（新しい列）… 実際に使うプラン
└─ work_logs（作業の記録。1 日の 1 作業で 1 行）
   ├─ work_log_targets（対象の畝。1 件の記録に複数）
   └─ work_log_inputs（使った資材）

work_types に列を足す … 計画に置ける種類か、記録だけの種類か

famic_imports（取り込んだ農薬登録情報の版）
famic_products（登録基本部。登録番号と有効成分）
famic_uses（登録適用部。作物ごとの使用基準）
```

### 4.1 `fields.active_plan_id`

圃場ごとに、実際に使うプランを 1 つ決めます。プランの欄で「このプランを使う」を選びます。

- 記録の入力で選べる畝と作付は、このプランのものだけです。
- 使うプランを決めていない圃場では、記録を入れられません。
- 使うプランは削除できません。先にほかのプランを使うプランにするか、使うプランを外します。
- 記録のあとで使うプランを替えると、前のプランへのつながりは残ります（前のプランを消せば、つながりは外れて、名前だけが残ります）。

### 4.2 `work_logs`（作業の記録）

| 列 | 内容 |
|---|---|
| `field_id` | 圃場 |
| `date` | 作業をした日（何日かかかった作業は、始めた日） |
| `end_date` | 何日かかかった作業の、終えた日（作業中なら、進んだ日）。1 日の作業は空（4.2.1） |
| `work_type` | 作業の種類 |
| `finishes` | この記録で、つながる計画の作業を終えたか |
| `spec` | 実際の仕様（jsonb）。作業の種類ごとに項目が違う。定植・播種なら株間、条間、条数、千鳥、粒数、植える深さ、マルチ穴など。畝立てなら実畦と通路の幅 |
| `note` | メモ |

計画の作業の実績の日は、記録から求めます。

- 開始: その作業につながる記録のうち、いちばん早い日
- 終了: `finishes` の付いた記録の終えた日（`end_date`。空なら `date`）。付いていなければ、まだ終わっていない（作業中なら、記録が進んだ日まで帯を出す）

`works.actual_start` と `works.actual_end` は使わなくなったので、消しました。

#### 4.2.1 何日かにわたる記録

以前は、記録は「1 日に 1 件」でした。何日もかかる作業は日ごとに記録を分け、計画の作業を「完了」にするときだけ、アプリが開始日と終了日の 2 件を作っていました。計画にない作業を何日かかけて行ったときは、日ごとに 1 件ずつ入れるしかありませんでした。

これを、**作業 1 回 ＝ 記録 1 件**に改め、記録に終了日（`end_date`）を足しました。終了日は始めた日より後の日だけを持ちます（同じ日なら空。DB の検査でも止める）。

- 1 件の記録で「10/15〜10/17 除草」のように期間を表します。1 日で終わる作業は、終了日を空にします。
- 記録の窓では、作業をした日の下に「終えた日（何日かかったときだけ）」の欄を付けます。作業をした日の「本日」は今日 1 日の作業にし、終えた日の「本日」は終えた日を今日にします。「1 日の作業」で終えた日を空に戻せます。計画の作業から開いたときは、計画の開始日と終了日が入ります。
- 作業の途中で記録するときは、終えた日にここまで進んだ日を入れ（1 日目だけなら空）、「この日で終わり」の印を外して保存します。工程表と作付の詳細では「作業中」と出します。今週やること・遅れている作業の「修正」は、作業中の記録があればそれを開くので、終えた日と「この日で終わり」を入れて保存し直します。
- 計画の作業の「完了」は、2 件ではなく、計画の開始日から終了日までの 1 件の記録を作ります。
- 実績の日は、記録の開始日（`date`）と終了日（`end_date`。空なら `date`）から求めます。工程表の実績の帯、作付の詳細、遅れの判定、後ろをずらす処理も、これを使います。
- 気温・降水量の列は、これまでどおり、作業を終えた日の値です。
- 防除の使用回数は、1 件の記録で 1 回のままです。2 日以上かけて 1 回ぶんを散布した場合も、1 回と数えます（4.6）。
- MCP サーバーの `get_records` も、開始日と終了日を返します。
- これまでの記録は、終了日を空（1 日の作業）として、そのまま読めます。日ごとに分けて入れた記録はそのまま残し、まとめたいものがあれば、記録の窓で直します。

「日付の範囲を入れると、日ごとの記録を自動で作る」形も考えましたが、記録の数が日数ぶん増え、使用回数や実績の帯をまとめ直す処理が要るので、採りませんでした。

### 4.3 `work_log_targets`（対象の畝）

1 件の記録に、対象の畝を何本でも付けます。品目でまとめて入れると、その品目の畝がすべて付きます。

| 列 | 内容 |
|---|---|
| `log_id` | 記録 |
| `planting_id` | 作付（畝立てから後の作業） |
| `bed_id` | 畝 |
| `block_id` | 区画。区画の作業では、畝と作付は空 |
| `work_id` | つながる計画の作業。1 件の実績に畝を何本も付けると、計画の作業も作付ごとに違うので、実績ではなく対象ごとに持つ。計画の「完了」「修正」から入力したときと、実績の窓でつなぐ印を付けたときだけ入る（5.5）。計画にない実績では空 |
| `label` | 記録した時点の名前（例: 「区画 A 畝 3 キャベツ」） |
| `crop_name` | 記録した時点の品目の名前 |
| `area_m2` | 記録した時点の面積。畝は、計画の図形から「畝の長さ ×（畝幅＋両隣との隙間の半分ずつ）」で求めた畝＋通路の面積（区画の中の畝の面積を足すと、区画の面積とほぼ同じになる）。区画の作業では区画の面積。基準散布量の計算に使う |
| `spray_l` | 防除で、その畝に散布した液の量（L）。品目ごとに入れた量を、その品目の畝に面積の比で分ける |

`planting_id`、`bed_id`、`block_id`、`work_id` は、どれも先が消えたら空になります（`on delete set null`）。

記録・対象・資材は、DB の関数 `field.save_work_log` で、1 つのトランザクションでまとめて保存します。対象と資材は、保存のたびに渡したもので置き換えます。

### 4.4 `work_log_inputs`（使った資材）

| 列 | 内容 |
|---|---|
| `log_id` | 記録 |
| `kind` | 種類（農薬、肥料、種苗、資材） |
| `reg_no` | 農薬の登録番号（農薬のとき）。FAMIC の登録番号で、取り込んだ表から選ぶ |
| `standard` | 記録した時点の使用基準の写し（jsonb）。登録番号、農薬名、総使用回数に数える有効成分と、品目（区画）ごとに、選んだ作物名、適用病害虫、使用方法、希釈倍数・使用量、散布液量、使用時期、本剤の使用回数、総使用回数。あとで登録が変わったり失効したりしても、記録したときの基準で読める |
| `fertilizer_id` | 肥料の銘柄（肥料のとき。いまの `fertilizers` を使う） |
| `name` | 名前。銘柄を登録していないもの、名前が分からないもの（「薬剤名不明」）は文字で入れる |
| `method` | 使い方（散布、土壌混和、種子・種球の浸漬、株元散布、灌注など） |
| `dilution` | 希釈倍率（例: 1000 倍） |
| `amount`、`unit` | 使った製品の量と単位（例: 2 g、20 mL） |

散布した液の量は、1 回の防除で混ぜた農薬に共通なので、資材ではなく対象の畝に持ちます（4.3 の `spray_l`）。製品の量は、液の量の合計と希釈倍率から計算できますが、実際に量った値を入れられるよう `amount` にも持ちます。

### 4.5 農薬の使用基準（FAMIC の農薬登録情報）

使用回数を確かめるには、銘柄ごとの有効成分と、作物ごとの使用基準が要ります。これは、農林水産消費安全技術センター（FAMIC）が[農薬登録情報ダウンロード](https://www.acis.famic.go.jp/ddata/index2.htm)で配布している CSV を、そのまま DB に取り込んで使います。

#### 配布されているもの

| ファイル | 中身 | 大きさの目安 |
|---|---|---|
| 登録基本部 | 登録番号、農薬の種類、名称、登録を有する者、有効成分、総使用回数における有効成分、濃度、混合数、用途、剤型名、登録年月日。有効成分ごとに 1 行（混合剤は複数行） | 約 6,000 行 |
| 登録適用部一・二 | 登録番号、作物名、適用場所、適用病害虫雑草名、希釈倍数使用量、散布液量、使用時期、本剤の使用回数、使用方法、有効成分①〜⑤を含む農薬の総使用回数など。登録番号の範囲で 2 つに分かれる | 合わせて約 10 万行 |

- 文字コードは Shift_JIS（cp932）で、カナに半角が混じります。取り込むときに、すべての文字を NFKC で全角にそろえ、名前はひらがなをカタカナにした検索用の列も作ります。
- ファイル名に反映日が入ります（例: `R0810210.zip`）。登録と失効の反映に合わせて、月に数回替わります。
- 値は人が読む文です（例: 「1000～2000倍」「収穫前日まで」「3回以内(植付前は1回以内､植付後は2回以内)」）。

#### テーブル

**`famic_imports`（版）**: 取り込んだファイル名、ページに書かれた反映日、取り込んだ日時、行数。

**`famic_products`（登録基本部）**: CSV の列をそのまま持ちます。

**`famic_uses`（登録適用部）**: CSV の列をそのまま持ち、次の列を足します。読み取れない値は空にし、元の文は必ず残します。

| 足す列 | 元の列 | 例 |
|---|---|---|
| 希釈倍数の下限・上限 | 希釈倍数使用量 | 「1000～2000倍」→ 1000、2000 |
| 散布液量の下限・上限（L/10 a） | 散布液量 | 「100～300㍑/10a」→ 100、300 |
| 収穫前日数 | 使用時期 | 「収穫7日前まで」→ 7、「収穫前日まで」→ 1 |
| 本剤の使用回数の上限 | 本剤の使用回数 | 「5回以内」→ 5 |
| 総使用回数の上限（有効成分ごと） | 有効成分①〜⑤を含む農薬の総使用回数 | 「3回以内(植付前は1回以内､植付後は2回以内)」→ 3。かっこの中の条件は数えず、文のまま出す |

取り込みは、表を丸ごと入れ替えます。前の版は残しません。記録には、記録した時点の基準を写して残すためです（4.4 の `standard`）。

#### 作物名の当てはめ

FAMIC の作物名には、品目の名前（「らっきょう」）のほかに、まとめた名前（「野菜類」「ねぎ類」など）があり、まとめた名前の書き方（「野菜類(…を除く)」の中身など）は農薬ごとに違います。そのため、品目と作物名の対応を前もって決めることはしません。防除を記録するときに、選んだ農薬に登録されている作物名の中から、品目（区画で選ぶときは区画）ごとに、当てはまると判断した作物名をユーザーが選びます（6.1.3）。

- システムは、当てはめが正しいかを判定しません。判定しないことで、指摘が出ないことを「正しい」の印と受け取られないようにします。窓には、当てはめは本人の判断で、使う前にラベルで確かめるよう書きます。
- 当てはまる作物名がない農薬は使えない（使えば法令に反する）ので、「該当なし」は選べません。登録番号のある農薬は、品目ごとに作物名と使い方を選ばないと保存できません。名前だけで入れる農薬（登録番号なし。例: 薬剤名不明の浸漬）は、これまでどおり保存できます。
- 初めの値は、前回の選択です。その品目に同じ農薬を使ったいちばん新しい記録の作物名と使い方、なければ、その品目でいちばん新しく選んだ作物名（この農薬の作物名にあるときだけ）を入れます。前回の選択は、記録の写し（`standard`）から探すので、別の表は持ちません。

#### 更新の確かめ方

`scripts/import_famic.py` が配布ページを読みます。field_plan の GitHub Actions（`.github/workflows/famic.yml`）が、週に 1 回これを動かします。Actions は、取り込み係の利用者でログインして、途中の表（`famic_products_next`、`famic_uses_next`）に分けて入れ、DB の関数 `field.famic_finish()` が行数を確かめてから本番の表と入れ替えます（4.8）。

1. ページにある ZIP のファイル名を、`famic_imports` の最新の版と比べる。
2. 替わっていれば、ZIP を取ってきて、読み取りの列を作り、1 つのトランザクションで表を入れ替え、`famic_imports` に 1 行足す。
3. 列の名前や数が前と違えば、取り込まずに失敗として知らせる（形式が変わったときに、黙って壊れた値を入れないため）。

#### 画面での使い方

- 防除の記録で、農薬を名前（または登録番号）で探して選ぶと、その農薬に登録されているすべての作物名と使用基準を読み込みます。品目ごとに作物名と、適用病害虫・使用方法の行を選ぶと、希釈倍数、散布液量、使用時期、使用回数が出て、記録に写します。
- 記録した農薬の登録番号が最新の版にないときは、「登録が失効している可能性がある」と出します。
- 総使用回数の数え方には、FAMIC の注意事項（[総使用回数についての注意事項](https://www.acis.famic.go.jp/ddata/soukaisuu.pdf)）があります。画面にもこのリンクを出します。

### 4.6 使用回数の数え方

作付ごとに、播種・定植の前（種子・種球の浸漬、育苗中の防除）から収穫までの記録を数えます。

- **本剤の使用回数**: その作付に付いた、その登録番号の記録の件数（何日かかけた 1 回の防除も、記録 1 件で 1 回）
- **有効成分の総使用回数**: その作付に付いた記録のうち、その成分を含む農薬の件数の合計。成分は、登録基本部の「総使用回数における有効成分」の列で数えます（「有効成分」の列とは違うことがあります）

数えた結果は、作付ごとに「使用回数」の表で見られます。記録を入れるときには、選んだ作物名の基準に照らして、次のことを指摘します。保存は止めません。作物名の当てはめが正しいかは指摘しません（4.5）。

- 本剤または有効成分の使用回数が、使用基準を超える
- 希釈倍率が、使用基準の希釈倍数の下限より濃い（下限より薄い分には指摘しない）
- 散布液量が、使用基準の範囲の外にある（品目ごとに、その畝の面積で 10 a あたりに換算して比べる）
- 粒剤などの面積あたりの使用量（「6kg/10a」「4~6kg/10a」「1~2g/m2」など）で、使った製品の量が、選んだ畝の面積の基準の合計を超える（少なく使う分には指摘しない。「g/株」「1穴当り」など面積あたりでない基準は、株数がわからないので文のまま出すだけ）
- 収穫の予定日（または収穫の記録）が、使用時期の日数より近い
- 総使用回数にかっこの条件があるとき（植付前と植付後で回数が違うなど）は、条件の文を出して、本人に確かめてもらう

育苗中の記録は、まだ畝に植えていないので、定植のときにつなぎます。育苗の播種の記録を、定植する予定の作付に付けておけば、そこでの防除も同じ作付に数えます。

### 4.7 農薬の使用基準の部分を切り離せるようにする

FAMIC のデータを使う部分は、ほかの部分から切り離せるように作ります。

| 切り離す部分 | 内容 |
|---|---|
| テーブル | `famic_imports`、`famic_products`、`famic_uses`、`rac_imports`、`rac_codes` |
| 取り込み | `scripts/import_famic.py`、`scripts/import_rac.py` と、それを動かす GitHub Actions（`.github/workflows/famic.yml`） |
| 画面 | 使用基準の選択、使用回数の表と指摘、失効の知らせ、農薬名の後ろの作用機構分類のアイコン（4.9）。画面のコードは `app/pesticide.js` と `app/rac.js` にまとめる |
| MCP サーバー | `get_pesticide_usage`、`get_records` の農薬の `rac` |

- この部分を外しても、防除の記録（農薬の名前、量、使い方、希釈倍率、散布液量）は、文字と数字で入れられるようにします。`work_log_inputs` の `reg_no` と `standard` は空のままになります。
- 外すかどうかは、`app/config.js` の `famic`（`false` で外す）で切り替えます。外したときは、画面にこの部分を出しません。取り込みは、GitHub Actions の `famic.yml` を止めます。MCP サーバーは、Supabase の秘密の値 `FIELD_FAMIC` を `false` にします。

### 4.8 取り込み係の利用者

GitHub Actions から気象の値と FAMIC の登録情報を入れるために、Supabase Auth に専用の利用者（取り込み係）を作ります。Actions の秘密の値には、この利用者のメールアドレスとパスワードを置きます（`FIELD_IMPORTER_EMAIL`、`FIELD_IMPORTER_PASSWORD`）。

- 取り込み係は `field.importers` に登録し、RLS で次のことだけを許します。計画や記録の表は読めません。
  - `weather_daily` の読み書き
  - FAMIC の版（`famic_imports`）を読むこと、途中の表に入れること、入れ替えの関数（`famic_begin`、`famic_finish`）を呼ぶこと
  - 観測所の番号を読むこと（関数 `weather_stations`。どの圃場かは返さない）
- DB の接続文字列（RLS を通らず、共用の DB のすべての表を読み書きできる）は、GitHub に置きません。秘密の値が漏れても、触られるのは気象と FAMIC の表だけです。
- パスワードは乱数で作り、秘密の値にだけ入れます。漏れた疑いがあれば、Supabase の管理画面か管理用の API で作り直し、秘密の値を入れ直します。

### 4.9 農薬の作用機構分類（RAC コード）のアイコン

同じ作用機構の農薬を続けて使わない（ローテーション防除）ための目安として、農薬名を出すところでは、名前の後ろに必ず作用機構分類のアイコンを付けます。

| 項目 | 内容 |
|---|---|
| コード | IRAC（殺虫剤）、FRAC（殺菌剤）、HRAC（除草剤）。クロップライフジャパンの「RACコード検索表」（商品名別）から、有効成分ごとのコードを `rac_codes` に入れる。有効成分の名前で `famic_products` と結ぶので、新しく登録された製品にも、既にある成分ならコードが付く |
| どの委員会か | 表の「21A(I\*), 39(F\*)」のような印のとおり。印がなければ、その成分を含む製品の用途（殺虫剤・殺菌剤・除草剤）。用途で決まらない成分と、表にない成分は、`scripts/import_rac.py` の `COMMITTEE` と `MANUAL` に、原表で確かめて書く |
| 出すコード | 製品の有効成分の順に、用途に合う委員会のコード（殺虫殺菌剤なら IRAC と FRAC）。同じコードは 1 つにまとめる |
| 分類のないもの | 天敵、展着剤、フェロモン剤など分類の対象外と、名前だけで入れた農薬は、灰色の「−」。表にない成分は、灰色の「?」 |
| 形 | IRAC はボトルのフタ（上が丸く、下が平ら）、FRAC は袋（上下に帯のある四角）、HRAC は斜めの葉（y = x^10 と、それを (0.5, 0.5) で点対称にした y = 1 - (1 - x)^10 にはさまれた形） |
| 色 | 現代農業 2018 年 6 月号「RAC コードでローテーション防除」の表にならう。作用機構の近いグループは同じ系統の色で、表にないコードは同じグループの色、なければ白地に黒い枠。HRAC は表にないので、作用機構のまとまりで色を決めた |
| 出すところ | 検索の結果、選んだ農薬、品目ごとの使用基準、希釈倍率の注記、基準散布量の文、指摘、実績の一覧、作付の詳細の作業の行、農薬の使用回数の表（本剤と有効成分）。文字しか出せない窓には「（IRAC 4A）」と書き添える |
| 表にない成分の知らせ | 週に 1 回の取り込みのあと、FAMIC の有効成分のうち表にないもの（用途が「その他」だけのものを除く）を、GitHub Actions の警告に出す |
| 説明 | アイコンを指すと説明を出し、離れると消す。クリック（スマホではタップ）すると出したままにし、外のクリックか Esc で消す。IRAC は「主要グループと一次作用部位」（サブグループは主要グループの説明）、FRAC は「作用機構：〇〇」「作用点：〇〇」、HRAC は「作用機構：〇〇」と、その製品でこのコードを持つ有効成分。文は、クロップライフジャパンの日本語訳の分類表（IRAC Ver.11.3、FRAC 2025 年 5 月、HRAC 2025 年 7 月。HRAC の 3 と 23 は定義の変わった 2026 年 2 月版の国内の表）による |
| 説明とほかの操作 | アイコンは、検索の結果のボタンや実績の一覧の行の中にある。アイコンのクリックは画面全体で先に受け、農薬を選ぶ、実績の窓を開く、などには渡さない。入力の窓を開いているときは、説明の箱を窓の中に置く（窓の外は操作できないため）。説明が出ているときの Esc は、説明だけを閉じ、入力の窓は閉じない |

## 5. 作業の種類

作業の種類を、**工程の作業**と**管理作業**の 2 つに分けます。工程の作業は、心土破砕から収穫・残渣処理まで、順番に進む作業です。管理作業は、作付の期間の中で、何度も繰り返し、ほかの作業と同じ時期に重なる作業です。


### 5.1 工程の作業

| 種類 | 対象 |
|---|---|
| 心土破砕、ロータリー、太陽熱消毒の用意、太陽熱消毒、緑肥の播種、緑肥の伐採（モア）、堆肥・石灰・基肥、すき込み（ロータリー） | 区画 |
| 育苗の播種 | 作付（定植する予定の作付） |
| 畝立て、マルチ張り、定植・播種、収穫、残渣処理 | 作付 |

- 計画の入力は「作業の計画」の表（ひな形、並べ直し）で、実績の入力は実績の窓で行います。
- 順番の確認（前の作業と重なっていないか、順番が逆でないか）の対象です。
- 遅れたときに、後ろの作業を実績に合わせてずらす対象です（7）。

### 5.2 管理作業

| 種類 | 中身 | 対象 |
|---|---|---|
| 防除 | 農薬（4.5〜4.7）。除草剤を使った除草も、防除として入力する | 作付または区画 |
| 追肥 | 肥料 | 作付 |
| 除草 | 手取り、草刈りなど（除草剤を使わないもの） | 作付または区画 |
| 灌水 | － | 作付または区画 |
| 株の手入れ | 間引き、摘葉、摘心、芽かき、誘引、摘果、摘花、土寄せ | 作付 |
| その他 | 発芽確認、資材の設置、資材の撤去、その他 | 作付または区画 |

- **計画を入力できます**。入力は、実績と同じ窓（6.1.2）で、窓の上の「計画／実績」を計画にして行います（「＋ 入力する」から開いた窓は、計画で開きます）。「作業の計画」の表（工程の作業を並べる表）には出しません。そのため、表を工程と管理作業に分ける必要はなく、スマホでも実績と同じように入力できます。
- 1 回の入力で、選んだ作付（区画）ごとに 1 件ずつ計画の作業（`works` の行）を作ります。一緒に入力した計画には、まとまりの印（`works.batch_id`）を付けます。
- 計画の予定の中身（株の手入れ・その他の中身、予定の農薬、選んだ作物名と使い方、希釈倍率、量、メモ）は、計画の作業の `detail`（jsonb）に持ちます。防除の計画で作物名と使い方を選べば、使用基準の表示（基準使用量、何回目か）も見られます。作物名を選ぶまで保存できない確認は、実績のときだけにします。
- 順番の確認の対象にはしません（ほかの作業と重なってよい）。「並べ直す」や、遅れたときに後ろの作業をずらす処理でも動かしません。
- 工程表では、その作付（区画）の計画の段に帯で出します。1 日の作業がほかの作業と同じ日に重なるときの描き方は、工程の作業と同じです（6.2）。帯はドラッグで動かせます（計画の移動）。帯を押すと、計画の窓が開き、中身を直したり、消したりできます。一緒に入力した計画があれば、「この畝だけ」か「一緒に入力した全部」かを選びます。
- **繰り返し**: 「7 日おきに 3 回」のような計画は、計画の窓の「コピーして足す（◯日後）」で足します。繰り返しの入力は、必要になってから考えます。
- **今週やること・遅れている作業**: 管理作業の計画も出します。「修正」は、計画の中身を入れた実績の窓を開きます。「完了」は、防除と追肥では実績の窓を開き（農薬や肥料の量を入れないと実績にならないため）、ほかは計画どおりの日で実績を作ります。

### 5.3 株の手入れ、その他の中身

株の手入れとその他は、窓で中身を選びます。中身は複数選べます（例: 摘葉と誘引を同じ日に）。

- 中身は、実績では仕様（`spec`）に、計画では `detail` の仕様に持ちます（例: `{"items": ["摘葉", "誘引"]}`）。
- その他で、中身の「その他」を選んだときは、何をしたかを短い文字で入れます（`{"items": ["その他"], "other": "支柱の撤去"}`）。
- 最近の実績、工程表、作付の詳細、MCP サーバーでは、「株の手入れ（摘葉・誘引）」「その他（発芽確認）」「その他（支柱の撤去）」のように中身も出します。
- 間引きは、残した株の間隔（株間）を仕様に入れられます。

### 5.4 これまでの種類の移し替え

発芽確認と資材の設置は、これまで独立した作業の種類でした。管理作業の形にするときに、これまでの実績を次のように移し替えます。

| これまでの種類 | 移し替え先 |
|---|---|
| 発芽確認 | その他（発芽確認） |
| 資材の設置 | その他（資材の設置） |

DB の書き換えになるので、先に表を書き出し、試しに流して取り消してから本番に入れます。

### 5.5 計画と実績のつなぎ方

実績が、どの計画を行ったものかのつながり（`work_log_targets.work_id`）は、ご本人がどこから入力したかで決めます。アプリが推測して自動でつなぐことはしません（工程の作業も管理作業も同じ）。

- **つなぐ**: 計画の「完了」、または「修正」から入力した実績は、その計画につなぎます。
- **つながない**: 「入力する」のボタンなどから入力した実績は、同じ日に同じ種類の計画があっても、つなぎません（計画にない実績）。
- **気づけるように**: 実績の窓で、対象の作付（区画）に、同じ種類の終わっていない計画があれば、「この作付には 10/20 の定植の計画があります」と書き添え、印を付けるとその計画につなぐ欄を出します。初めは印なしです。実績を直す窓でも、同じ欄でつなぐ・外すを変えられます。
- **これまでのつながり**: 決め方を変える前に自動でつないだ実績は、そのまま残します。

決め方を変えた理由: 防除のように繰り返す作業では、「同じ種類で、まだ終わっていない最初の計画」に自動でつなぐと、計画にない臨時の防除が、来週の防除の計画を「完了」にしてしまうためです。

### 5.6 未実施と取りやめ

「未実施」は、記録がない状態です。予定日を過ぎても記録がない計画の作業を「遅れている作業」として出します。やらないことにした作業は、計画の作業に「取りやめ」の印を付けます。`works` に、取りやめた日（`cancelled_on`）と理由（`cancel_note`）の列を足します。取りやめは、記録を入れる画面から行います（6.1.2）。

## 6. 画面

### 6.1 スマホ

圃場で入れる場面が主なので、スマホで記録を入れられるようにします。スマホはいま閲覧だけなので、この機能で初めて書き込みができるようになります。書き込めるのは、記録の入力と修正、計画の作業の「完了」と「取りやめ」だけです。計画はいままでどおり PC で直します。

#### 6.1.1 日程の画面

上から次の順に並べます。

| 欄 | 内容 |
|---|---|
| 確認が必要な点 | 日程に無理があるときだけ出す。見落とさないように、いちばん上に置く |
| 遅れている作業 | 予定日を過ぎて完了していない計画の作業。何日遅れか、記録があればいつ始めたかを出す。行ごとに「完了」と「修正」のボタン |
| 今週やること | いまの欄の行ごとに「完了」と「修正」のボタンを足す。完了した作業は ✓ と実施日を付けて薄くし、「修正」から記録を開ける |
| 最近の記録 | 計画にない作業も含めて、新しい順に数件。「すべて」で記録の一覧へ |
| 区画と畝、作業の計画、工程表 | いままでどおり。区画と畝の図では作業の名前の横に済みの印を付け、作業の計画の表には実績の列を足し、工程表には表示の切り替えを足す（6.2、6.4） |

行のボタンは次の 2 つです。

| ボタン | 動き | 向いている作業 |
|---|---|---|
| 完了 | 計画どおりに行ったときに押す。画面を開かずに、計画の日で、その計画の作業につながった記録を作る。計画が 1 日ならその日に完了（`finishes`）の記録を 1 件、何日かにわたるなら開始日の記録と終了日の完了の記録の 2 件を作り、実績が計画どおりの期間になるようにする。同じ日の同じ作業を畝ごとにまとめた行は、まとめて記録になる | 計画どおりに行い、内容を残す必要のない作業（畝立て、マルチ張りなど） |
| 修正 | 記録を入れる画面（6.1.2）を、計画の作業から値を入れた状態で開く。内容を入れて保存すると完了になる。この画面で取りやめにもできる | 内容を残したい作業（定植・播種の仕様、防除の農薬など）、日付が今日でない作業、取りやめる作業 |

- 完了した行の「修正」は、その記録を直す画面を開きます。
- 画面の右下に、いつでも押せる「記録する」のボタンを置きます。計画にない作業（灌水など）は、ここから入れます。PC の日程の画面にも、同じボタンを置きます（6.4）。

#### 6.1.2 記録を入れる

1 つの画面に、上から次の順に並べます。

1. **作業をした日**: 初めは今日（計画の作業の「修正」から開いたときは計画の日）。右の「本日」のボタンを押すと、押した日の日付が入る。
2. **作業の種類**: よく使う種類を大きめのボタンで並べ、ほかは「ほか…」から選ぶ。
3. **対象**: **品目でまとめて選ぶ**のが初めの形です。その日に畝にある作付（その日までに始まった作付のうちいちばん新しいもの。まだ始まっていなければ次の作付。始まった日は、記録があれば最初の記録の日、なければ計画の最初の作業の日）を品目ごとに並べ、品目にチェックを入れると、その品目の畝がすべてチップで付きます。チップを押すと、その畝だけ外せます。「図から選ぶ」で、区画と畝の図から畝を選ぶこともできます。選んだ畝の面積（畝＋通路、4.3）の合計を出します。
4. **仕様、資材**: 作業の種類に合わせた欄を出します。定植・播種なら株間、条間、条数など。防除は 6.1.3。
5. **メモ**
6. **記録する**: 画面の下に固定します。

計画の作業とのつながりは、5.5 の決め方で付けます（自動ではつなぎません）。つながった計画があるときに「この日で終わり」を選ぶと `finishes` が付きます。

窓の上に「計画／実績」の切り替えを置き、管理作業の計画も同じ窓で入力します（5.2）。計画のときは、使った量、散布した液の量、使用基準の写しなど、実績にしか要らない欄は出しません。画面の言葉は、窓の題が「実績を入力する」「計画を入力する」「実績を直す」「計画を直す」、ボタンが「入力する」です。

**開き方による違い**

| 開き方 | 初めに入っている値 |
|---|---|
| 「記録する」のボタン（スマホと PC の日程の画面。6.1.1、6.4） | 日付（今日）だけ |
| 作付の詳細の「この作付の記録を入れる」（6.3） | 日付（今日）と、対象にその作付の畝。作業の種類は空 |
| 未完了の計画の作業の「修正」（6.1.1） | 日付（計画の日。「この日で終わり」に印が付くので、何日かにわたる作業は計画の終了日）、作業の種類、対象の畝、計画の作業とのつながり。「この日で終わり」に印。定植・播種なら、仕様の欄に計画の値（株間、条間、条数など）を入れておき、違うところだけ直せるようにする |
| 完了した行の「修正」、記録の一覧、作付の詳細の実績の日付（6.1.4、6.3） | その記録の値 |

**取りやめ**: 未完了の計画の作業の「修正」から開いたときだけ、画面の下に「この作業を取りやめる」を出します。押すと確かめたうえで、記録は作らずに、計画の作業に取りやめの印と日付を付けます。メモ欄に書いた文は、取りやめの理由として計画の作業に残します。取りやめた日は、押した日（今日）です。取りやめた作業は、遅れている作業と今週やることから外れ、作付の詳細の実績の欄には「取りやめ」と出します。作付の詳細で「取りやめ」を押すと、取りやめを元に戻せます。

#### 6.1.3 防除の入力

1. **農薬**: 名前か登録番号で探します。1 回の防除で混ぜる農薬が複数あれば、「もう 1 剤」で足します。
2. **作物名と使い方・適用病害虫**: 品目ごとに（区画で選ぶときは区画ごとに）、その農薬に登録されている作物名の一覧から当てはまるものを選び、その作物名の行から使い方・適用病害虫を選びます。作物名が多い農薬では絞り込みの欄を出し、長い名前も折り返して全部見せます。初めの値は前回の選択で、「前回の選択を入れています」と書き添えます。選び終えるまで保存できません（4.5）。
3. **品目ごとの基準**: 選んだ品目ごとに、選んだ作物名の基準で、次を並べます。
   - 畝＋通路の面積
   - 使用基準（希釈倍数、散布液量、使用時期）
   - **この面積の基準散布量**（散布液量の基準 × 面積。例: 100〜300 L/10 a × 33.6 ㎡ → 3.4〜10.1 L）
   - この防除で、その成分の何回目になるか（上限も）
4. **希釈倍率**: 初めは、選んだ品目の希釈倍数の下限（いちばん濃くしてよい倍率）のうち、いちばん大きいものにします。例: 1000〜1500 倍の品目と 2000 倍の品目なら 2000 倍。薄くする分には基準を外れないので、どの組み合わせでも 1 つの倍率が決まります。どの品目に合わせたかを書き添え、倍率は直せます。
5. **基準散布量の合計と製品の量**: 基準散布量の合計と、希釈倍率から計算した製品の量を出します（例: 6.7〜16.8 L → 製品 3.4〜8.4 mL）。散布する前に、作る液の量を決めるためです。
6. **実際に散布した液の量**: 品目ごとに入れます。合計と、希釈倍率から計算した製品の量を出します。
7. **指摘**: 4.6 の指摘を、この画面の中に出します。保存は止めません。
8. **粒剤など**: 選んだ使用基準が面積あたりの使用量で、希釈倍数がない農薬（作物名を選ぶ前は、剤型が粒剤・粉剤のもの）は、希釈倍率と散布した液の量を入れません。使った製品の量だけを入れ、品目ごとの「この面積の基準使用量」（例: 6kg/10a × 36.8 ㎡ → 220.8 g）と、その合計を出します。

#### 6.1.4 記録の修正と削除

記録の一覧（日程の画面の「最近の記録」から開く）で、記録を選んで直したり消したりします。直す画面は、入れる画面と同じです。

### 6.2 工程表

日程の画面の工程表に、表示の切り替えを足します。新しいタブは作らず、振り返りは工程表と作付の詳細（6.3）で行います。

| 表示 | 内容 |
|---|---|
| 計画 | 計画の作業の帯を、作業の種類の色で出す |
| 実績 | 実績の日を帯にする。計画の作業につながった実績は開始から終了まで、計画にない実績（灌水、防除など）は実績の日だけ |
| 計画と実績 | 区画（畝）ごとに 1 行にし、計画は太い帯、実績は計画の帯の下側に重ねた細い帯で出す。実績のある計画の帯は薄く出す（作付の詳細の「工程」と同じ描き方） |

- **行の作り**: 1 行が 1 つの区画（畝）です。左に名前の列を置き（横に送っても残る）、右に帯を並べます。名前だけの行と、「計画」「実績」の見出しの行は置きません。
- **表示期間**: 「全体」「3 か月」「1 か月」から選びます。選んだ期間がちょうど画面の幅に収まるように、1 日の幅を決めます（3 か月と 1 か月は今日を中心に。1 日が 5px より狭くなるときだけ横に送る）。作業のある範囲は全部描くので、期間の外は横に送って見られます。選んだ期間は、圃場ごとに覚えます。
- **帯の大きさ**: 計画の帯は高さ 26px で、幅に余裕があれば中に作業の名前を書きます。1 日の作業も 12px より細くしません。
- **名前のリンク**: 区画の名前、畝の番号、品目の名前を押すと、詳細（6.3）を開きます。畝の番号は、今日その畝にある作付です。1 本の畝に作付が複数あるとき（「畝3 レタス → ニンジン」）は、品目の名前ごとにリンクにします。下線と、指したときの色の変化は付けません。
- **行の選択**: 行の帯のない所、計画の帯、実績の帯を、動かさずに押して離すと、その区画（畝）を選びます（行全体の背景を薄い色にする）。選んだ行は、貼り付けの入れ先と、「＋ 入力する」の対象（畝なら今日その畝にある作付、区画なら区画で選ぶ）になります。管理作業の計画の帯は、行を選んだうえで、計画の窓（5.2）も開きます。下の「作業の計画」で開く区画（畝）は、工程表の操作では切り替えません（工程表から離れた所にあり、切り替わったことに気づきにくいため）。「区画と畝」の図と、「確認が必要な点」の行で選びます。
- **計画の帯のドラッグ**: 「計画」と「計画と実績」の表示で、ドラッグで日程を動かせます。別の行へ動かすと移し（Ctrl を押しながら離すとコピー）、畝へ入れるときは、その日が期間に入る作付に入れます。
- **同じ日に重なる帯**: かかる日数が 1 日の作業は、前後の作業と同じ日に重ねられる（README の日程の指摘を参照）。1 日の作業と何日かの作業が同じ日に重なったときは、その日は 1 日の作業を描き、何日かの作業はほかの日に普通の高さで描く（例: 5 日の作業の初日に 1 日の作業があれば、初日は 1 日の作業、残りの 4 日は 5 日の作業）。同じ日に 1 日の作業が 2 つ以上あるときだけ、その日の中で上下の段に分ける。何日かの作業どうしが重なったときは、どの帯も隠れないよう、上下の段に分ける。実績の帯も同じ（上下に分けるときは、計画の帯と同じ高さを分ける）。
- **実績の帯のドラッグ**: 実績の帯も、横にドラッグすると、もとになった実績の日付を、動かした日数だけ動かせます（PC の幅のとき）。「完了」を押した日と実際に行った日が違うときに、実績を開かずに直すためです。1 件の実績がほかの畝にも付いているとき（まとめて完了にした畝など）は、その畝だけを動かす（その畝の分を別の実績に分ける）か、実績ごと動かすかを尋ねます。日付のほかの内容は、作付の詳細から実績を開いて直します。
- **表示を覚える**: 選んだ表示（計画／実績／計画と実績）と表示期間は、表示日や開いていたプランと同じく、ブラウザーが圃場ごとに覚えていて、次にその圃場を開いたときも同じ表示になります。表示は、工程表と作付の詳細で 1 つの設定を共有します。
- **凡例**: 表示している作業の種類だけを出します。「計画と実績」では、薄い計画の帯と細い実績の帯の見本も出します。
- **PDF 出力**: 表示期間によらず、作業のある範囲の全体を、紙の幅に収めて出します。

### 6.3 作付の詳細

作付 1 つについて、計画と実績を 1 つの画面で見ます。PC で見る画面ですが、スマホでも閲覧できます。

#### 上の部分

- 作付の名前（例: 「区画A 畝4 リーフレタス」）、マルチの有無、畝＋通路の面積、苗数、収穫完了予定日を、頭の真ん中に出す。工程表へは上の「日程」のタブで戻る（はじめは「工程表に戻る」のボタンを置いていたが、タブと同じ動きなので外した。2026-11-08）。
- 「日記 n 節（最新 M/D）」と「＋ 作業を入力」のボタン（この順）は、名前の右隣に置いて 1 行に収まればそこに、収まらなければ 2 行目に右詰めで置く。幅が変わるたびに測り直す。スマホの幅では、面積・苗数を名前の下の行に回し、前後の作付のボタンは畝の番号と品目のあいだで折り返してよい。
- 詳細は URL（`#detail/planting/作付の ID`、区画は `#detail/block/区画の ID`）を持ち、開くときにブラウザーの履歴に積みます。ブラウザーの戻るボタンで日程に戻り、再読み込みしても詳細のまま開きます。隣の作付へ移るときは URL を置き換え、履歴は積まないので、何本か見てからでも、戻る 1 回で日程に戻ります（上のタブの移り方は README を参照）。
- 隣の畝の作付へ移るボタン（「‹ 畝3 ニンジン」「畝5 リーフレタス ›」）を、名前の両側に、日記の「‹ 前の日」「次の日 ›」と同じ文字だけの形で置く。工程表に戻らずに、順に見ていけます。
- 「＋ 作業を入力」のボタン。記録を入れる画面を、対象にこの作付の畝を入れた状態で開きます（6.1.2）。
- 「計画／実績／計画と実績」の切り替え。工程表と同じ設定です（6.2）。

#### 工程

作業の種類ごとの行に、帯を並べた小さな工程表です。区画の作業（ロータリー、基肥など）も「区画の作業」の行に出します。

- 「計画と実績」では、計画の帯を薄く太く、実績の帯を濃く細く重ねます。「計画」「実績」では、どちらか一方だけです。
- **作業のない期間は詰める**: 作業のある日の前後 1 日を残し、3 日以上の空きは、斜線の細い帯に詰めて、下に日数（例: 「29 日」）を書きます。収穫まで間があっても、作業の多い時期が広く見えます。
- 今日の位置に線を引きます。

#### 計画との差

「計画と実績」の表示のときだけ出します。

- 定植・播種の記録の仕様（株間、条間、条数など）が計画の値と違えば、差を書きます。計画は、計画として残します（書き換えません）。
- 記録の仕様が品目の設定値（作付に値を入れていないときに使う値。次に作付を作るときの初期値）とも違えば、「品目の設定値を記録に合わせる」を出します。押すと、確かめてから品目の設定値を変えます。品目の設定値を使っている作付のうち、今回の作付と、そのプランですでに始まった作付には、変える前の値を写しておくので、計画は変わりません。まだ始まっていない作付は、新しい設定値になります（ほかの圃場とプランも同じです）。品目の一覧にない品目の作付では、ボタンを出さずに、その旨を書きます。
- 実績の終了日が計画とずれていれば、「後ろを実績に合わせて並べ直す」を出します（7 章）。

#### 作業の表

| 列 | 内容 |
|---|---|
| 作業 | 作業の種類（色の印と名前）。区画の作業には「区画A の作業」、計画にない作業には「計画にない作業」と添える |
| 計画 | 計画の日と、計画の内容（仕様、苗数、施肥量など） |
| 実績 | 記録の日と、記録の内容（仕様、農薬と量、使用回数、メモ）。使用回数が上限に届いたときなどの指摘（4.6）も、ここに出す |
| ずれ | 計画と実績の日のずれ（例: 「1 日遅れ」「予定どおり」） |
| 気温・降水量 | 定植・播種の日以降に記録がある行だけ。その日の平均気温と降水量を大きく、その下に、定植からその日までの積算温度と積算降水量を小さく出す。温度どうし、降水量どうしをまとめ、色も分ける（温度は茶、降水量は青）。2 日にまたがる記録は、終わった日の値。欠測の日は「欠測」と出す |

- 計画の作業と、それにつながる記録を同じ行に並べます。計画にない作業の記録は、計画の欄を「－」にします。
- 予定日を過ぎて記録のない計画の作業は、実績の欄に「未実施」と出します。
- 行は日付の順です。3 日以上作業のない期間には「作業のない期間 ◯ 日」、今日の位置には「今日」の区切りの行を入れます。
- 「計画」の表示では、計画の列だけを出します。「実績」の表示では、記録の行と実績、気温・降水量の列だけを出します。ずれの列は「計画と実績」のときだけです。
- **押したとき**: 実績の日付を押すと、実績を直す窓（6.1.2 と同じ内容）を開きます。計画の日付を押すと、計画を直す窓を開きます。管理作業の計画は、実際に使うプランなら入力の窓（計画を直す。5.2）で、中身や対象まで直せます。工程の作業の計画（と、実際に使うプランでない管理作業の計画）は、開始日、終了日、メモを直す小さな窓です（開始日を動かすと、日数を保って終了日も動く）。計画の欄の日付のほかの所を押すと、日程の画面の「作業の計画」で、その区画（作付）を開きます。

#### 右の欄

| 欄 | 内容 |

| これから 2 週間の予報 | 8.7 の予報を、1 日 1 行で並べる。列は日（曜日）、天気（アイコンだけ）、気温（最高と最低の 2 行）、降水確率、風（風向の矢印と、風の強さの 2 行）。出す項目が変わる 3 日目と 7 日目の後ろに区切り線を引く |

## 7. 遅れへの対応

完了のボタン、遅れている作業、工程表と作付の詳細の実績、区画と畝の図の済みの印、作業の計画の表の実績の列は、開いているプランが実際に使うプランのときだけ出します。記録がつながるのは、実際に使うプランの作業だけだからです。

- **計画は自動では動かさない**: 勝手に書き換えると、元の計画が分からなくなるためです。
- **「実績に合わせて後ろを並べ直す」**: 区画や作付ごとに、最後に終わった作業の実績の終了日と計画の終了日の差の日数だけ、そのあとの終わっていない作業をずらします。作業どうしの間隔と日数は保ちます。目安の日数で並べ直すと、品目の設定値のない作付で収穫までの間隔が消えたり、計画で手で空けた間隔が崩れたりするためです。
- **指摘**: 実績のある作業は、計画の日ではなく実績の日で、前後の間隔を見ます。

## 8. 積算温度・積算降水量と予報

`fields` の基準点の緯度と経度で、日ごとの平均気温と降水量を取り、定植・播種の日から積算して、作付の詳細に出します（6.3）。定植・播種の日は、計画と実績の両方があれば実績を優先し、定植・播種の記録があればその最初の日（計画の作業につながっていない記録も含む）、なければ計画の定植・播種の日です。これからの予報も、同じ画面に出します（8.7）。

### 8.1 方針

| 値 | 取り先 |
|---|---|
| 気温 | 気象庁のアメダス |
| 降水量 | 気象庁のアメダス。近くに雨量計がなければ、JAXA の GSMaP（衛星から推定した雨量）で補う |
| 圃場の気温（任意） | 圃場に置いた温度ロガー。置いたときだけ使う |

取った値は、日ごとの気象データの表に入れておき、画面ではそれを足し合わせます。表は全圃場で共通にします。

### 8.2 衛星の地表面温度を使わない理由

衛星の地表面温度（JAXA の GCOM-C など）は、地面そのものの温度で、積算温度に使う気温（地上 1.5 m ほど）とは違います。晴れた日中の裸地やマルチでは、気温より 10 ℃ 以上高くなります。また、雲の下は値が欠け、衛星が通る時刻の値なので日平均になりません。格子（日別の値で 4〜5 km）も圃場より大きいため、使いません。

### 8.3 アメダスの取り方

| 取る値 | やり方 |
|---|---|
| 正式な値 | GitHub Actions（`.github/workflows/weather.yml`）が毎日 1 回、`scripts/fetch-weather.mjs` で、気象庁の「過去の気象データ」の日別の表（月ごとのページ）を読み、前の月と今月の日ごとの値を入れる（`source` は `jma`）。品質を確かめた正式な値で、昨日の分まで、いつの日の分も取れる。あとで直された値も、前の月までさかのぼって拾う。古い分は、日付を渡して流すと入れ直せる |
| 表示用の値（予備） | 日別の表にまだない日と、日別の表の地点が見つからない観測所は、気象庁のサイトが表示に使っている JSON（10 分ごとの値）から求める（`source` は `amedas`）。アプリも、開いたときに、まだ表にない直近の日をこの JSON から取る（Actions が止まったときの予備）。正式な値があれば上書きしない |

- 日別の表は、ブラウザーから読めない（CORS を許していない）ので、Actions だけが読みます。Actions は、取り込み係の利用者でログインして書き込みます（4.8）。
- 日別の表の地点は、アメダスの観測所の番号の上 2 桁（府県の番号）で府県の地点の一覧を読み、名前と緯度経度（2 km 以内）で突き合わせて求めます。気象台などの観測所（種類 s）とアメダス（種類 a）で、表の列が違います。
- 表の印は、「)」（準正常値）は使い、「]」（資料不足値）、「×」（欠測）、「#」（疑わしい値）は欠測とします。「--」（現象なし）は、降水量では 0 です。
- 表示用の JSON は、11 日前までしか残らず、ときどき値が抜けます（毎正時の値が 20 回分に満たない日は、日平均気温を欠測にします）。最高・最低気温も、10 分ごとの値から選ぶので、正式な値より控えめになります。正式な値を優先するのはそのためです。
- 出典として「気象庁のデータを加工して作成」と、画面に書きます。

### 8.4 観測所の選び方

- 圃場ごとに、気温の観測所と雨量の観測所を別々に選びます。気温を測る観測所は、雨量だけの観測所より少ないためです。
- 圃場の画面に、基準点から近い順に観測所と距離を出し、そこから選びます。観測所の一覧（番号、名前、緯度と経度、測っている要素）は、気象庁の観測所の一覧から取り込みます。
- 観測所が欠測の日は、積算に穴が開いたことを画面に出します。ほかの観測所の値で埋めることはしません。

### 8.5 GSMaP で雨量を補う（まだ作っていない）

- 雨量の観測所が遠いときだけ使います。GSMaP は約 10 km の格子で、1 時間ごとの雨量です。日ごとに足して表に入れます。
- 推定値なので、アメダスの値と並べるときは、どちらの値かを必ず分けて出します。
- 出典として「JAXA GSMaP」と、画面に書きます。

### 8.6 温度ロガー（任意。まだ作っていない）

- 圃場にロガーを置くと、圃場そのものの気温が取れます。値は CSV で取り込みます。
- ロガーの値がある日は、積算にロガーの値を使います。ない日はアメダスの値を使います。
- 数か月ぶんの値がたまれば、アメダスとの差を見て、ロガーのない時期の値の補正に使えます。補正するかは、値がたまってから決めます。

### 8.7 予報

気象庁の予報を、圃場の予報区で取ります。アメダスと同じく、気象庁のサイトが使っている JSON から取るので、仕様の保証はありません。取れなかったときは、予報の欄に「予報を取れませんでした」と出します。

| 期間 | 取るもの | 元の予報 |
|---|---|---|
| 1〜3 日目 | 天気、最高・最低気温、降水確率、風（風向と、「やや強く」「強く」などの強さ） | 府県天気予報 |
| 4〜7 日目 | 天気、最高・最低気温、降水確率 | 週間天気予報 |
| 8〜12 日目 | 最高・最低気温 | 2 週間気温予報（気象庁が出しているのは 12 日目まで） |

- 気象庁の予報には、降水量（mm）と、風速の数値（m/s）がありません。降水は降水確率だけを出し、風の強さは「ふつう」「やや強い」「強い」の 3 段階で出します（予報の文に強さの言葉がなければ「ふつう」）。風向は、予報の文の最初の風向を矢印にします。
- 8〜12 日目の気温は、1〜7 日目の予報より確からしさが下がるので、薄い色で出します。
- 府県天気予報と週間天気予報は、ブラウザーから直接読みます。2 週間気温予報は、ブラウザーから読めない（CORS を許していない）ので、Supabase の関数 `field-weather` を通して読みます。関数はログインした利用者だけが呼べます。
- 予報は DB に持たず、作付の詳細を開いたときに読みます（30 分は同じものを使います）。
- 圃場の予報区（府県予報区と予報の区域）、予報の気温の地点、2 週間気温予報の地点は、観測所と同じく圃場ごとに選びます（圃場図の「気象」の欄）。
- 予報の表の下には、出典だけを書きます。選んだ区域と、2 週間気温予報の地点の名前も書きます（「出典: 気象庁の予報（本島北部の府県天気予報・那覇の 2 週間気温予報）を加工して作成」）。2 週間気温予報を読めなかったときは、同じ行の先頭に「2 週間気温予報を読めませんでした。」と出し、出典から 2 週間気温予報を外します。2 週間気温予報の地点の選択肢は、気象庁が予報のデータを出している地点だけにします（一覧には、データを出していない地点も多く入っているため）。

## 9. MCP サーバー

`field-mcp` に、記録を返す道具を足しました。

| 道具 | 返すもの |
|---|---|
| `get_records` | 期間、品目、作業の種類、場所で絞った記録（対象の畝、仕様、資材、メモ、つながる計画の作業） |
| `get_pesticide_usage` | 作付ごとの、農薬の本剤と有効成分の使用回数と、使用基準。FAMIC のデータを使うので、4.7 の切り離せる部分に入れる |

サーバーの説明は、これまで「返すのは計画で、実際に行った作業の記録ではありません」でした。計画と記録の両方を返すこと、記録の道具では「行った」と書いてよいことに書き換えました。

- Supabase の秘密の値 `FIELD_FAMIC` を `false` にすると、`get_pesticide_usage` と、その説明を外します（4.7）。
- `list_fields` と `list_plans` に、実際に使うプランを足しました。`get_plan` と `get_schedule` の作業には、取りやめた日（`cancelled_on`）を付けます。

## 11. 農作業日記と写真

11.1 は作成済みです（使い方は README の 9 章）。11.2 と 11.3 は、いまは取り組みません。

### 11.1 農作業日記をこのアプリで書く

#### ねらい

農作業日記は、これまで Google ドキュメントに書き、書き出したものを `inoo_farm` のスクリプトで `diary` スキーマに取り込んでいました。この形には、困ることが 2 つありました。

- 1 つのファイルが長くなり、スマホで書き足すときのスクロールが大変。
- 書いたあと、DB への取り込みを別に行う必要がある。

日記をこのアプリで書き、DB に直接保存するように改めます。写真は、いまの日記と同じく文中に入れられるようにします。日記は 1 日ずつ書きます。見るときは、カレンダーで日・週・月を選んで並べて読めるようにし、語で探せるようにもします。

#### 決めたこと

| 項目 | 決めたこと |
|---|---|
| 切り替え | 2026-11-07 に切り替えた。この日までの日記は、Google ドキュメントから取り込み済み。これ以後は Google ドキュメントには書かず、このアプリだけで書く |
| 正本 | 1 日 1 行の Markdown（`diary.days`）。写真は文中に `![](…)` で書く。見出しごとの節（`diary.sections`）は、保存のたびに Markdown から作り直す |
| 作物と作業の種類（タグ） | 保存のときに語で自動で付け、画面で直せる形で始めた。2026-11-08 に、Claude Code が本文の意味と写真の中身から付ける形に改めると決めた（下の「作物と作業の種類」） |
| LINE | このアプリには出さない。取り込みは、これまでどおり `inoo_farm` のスクリプトで行う |
| 写真 | 1 種類だけ保存する（短辺 1080 px、品質 85 の JPEG）。SNS にそのまま使える大きさ。撮影日時と元のファイル名を残し、もっと大きい写真が要るときは Google フォトの元の写真を探す |
| 写真のバックアップ | DB の世代ごとのバックアップには載せず、新しい写真だけを R2 に 1 回写す（差分） |
| 画面 | 上のタブに「日記」を足し、「圃場図　日程　品目　日記　履歴」の並びにする |
| diary-mcp | `diary.sections` の形は変えない。写真の置き場の並びが変わるので、`get_photos` を直す |
| 置き場所 | コードは field_plan（公開のリポジトリ）に置く。日記の中身は DB と非公開のストレージにだけ置き、テスト用のデータにも本物の日記を使わない |

#### 日記を守る仕組みは変えない

日記には、ほかの方の氏名や連絡先が入ります。`inoo_farm` の README の「日記を守る仕組み」を、そのまま保ちます。

- `diary` スキーマは、Supabase の API（Exposed schemas）に出しません。
- 画面からの読み書きは、`field` スキーマに置く関数（下の表）だけを通します。関数は `security definer` で、最初に `field.is_owner()` を確かめ、本人でなければ何もせずに止めます。
- 写真の置き場（`diary-photos`）は非公開のままにします。本人（`field.is_owner()`）だけが上げて読めるよう、許可（policy）を足します。

#### テーブル

`diary.sections` と `diary.messages` は、いまのまま使います。次のテーブルを足します。定義は `inoo_farm` の `sql/diary.sql` に足します。

| テーブル | 中身 |
|---|---|
| `diary.days` | 1 日 1 行。`entry_date`（主キー）、`title`（その日の題）、`body`（Markdown。写真の位置もそのまま）、`tags`（作物と作業の種類を直した内容。下記）、`updated_at` |
| `diary.day_history` | 保存する前の版。`entry_date`、`body`、`tags`、`saved_at`。Google ドキュメントの版の履歴の代わりで、消してしまった文を取り戻すために使う |
| `diary.tag_words` | 作物と作業の種類を見分ける語。いまの `config/tags.json` を移したもの |
| `diary.photos` | 写真 1 枚 1 行。`name`（主キー。例: `2026-11-08_01.jpg`）、`entry_date`、`taken_at`（撮影日時）、`original_name`（元のファイル名）、`width`、`height`、`uploaded_at`。撮影日時と元のファイル名は、取れなければ空 |

`diary.sections` の行は、`diary.days` を保存するたびに、その日の分だけ消して作り直します。`id`（例: `2026-11-08-02`）、見出し（`path`）、本文、写真（`images`）の作り方は、`inoo_farm/scripts/build_sections.py` と同じにします。

#### 読み書きの関数

| 関数 | 働き |
|---|---|
| `field.diary_save_day(date, title, body, tags, sections, expected)` | 前の版を `diary.day_history` に残し、`diary.days` を書き、その日の `diary.sections` を作り直す。1 つのトランザクションで行う。節への分け方は画面（`app/diary.js` の `splitSections`）が行い、種類は DB（`diary.section_tags`）が付ける。`expected` は画面が読んだときの `updated_at` で、違えば、ほかの画面で書き換えられているので止める。どこからも使われなくなった写真の名前を返す（置き場のファイルは画面が消す） |
| `field.diary_get_days(from, to)` | 期間内の日記（Markdown と、節ごとの作物と作業の種類、写真の撮影日時と元のファイル名）を、日付の順に返す |
| `field.diary_calendar(from, to)` | 日記のある日と、その日の写真の枚数を返す（カレンダーの印に使う） |
| `field.diary_search(words)` | 語をすべて含む日を、新しい日から 200 日まで返す。前後の文は画面が切り出す |
| `field.diary_tag_names()` | 作物と作業の種類の名前の一覧（画面で直すときの選択肢） |
| `field.diary_photo_names(date)` | その日の写真の名前（新しい写真の通し番号を決めるのに使う） |
| `field.diary_add_photo(...)` | 上げた写真を `diary.photos` に記録する |

検索は、語の部分一致（`ILIKE`）で行います。日本語は、通常の全文検索では語に分けられないためです。日記は数百日分なので、索引がなくても速さは問題になりません。

#### 写真

写真は 1 種類だけ保存します。いまの「元の写真」と「縮小版」の 2 種類はやめます。

- **大きさ**: 短辺 1080 px、品質 85 の JPEG。元が小さいときは広げません。Instagram の横幅（1080 px）に、縦向きの写真でも横向きの写真でも足り、diary-mcp がすすめた写真をそのまま投稿に使えます。SNS は投稿をもう一度圧縮するので、品質はいまの縮小版（78）より上げます。1 枚はおよそ 0.25 MB で、Supabase の無料の枠（Storage 1 GB）に数年分入ります。
- **元の写真は保存しない**: 元の写真は、スマホと Google フォトに残ります。拡大して確かめたいとき、もっと大きい写真が要るときは、`diary.photos` の撮影日時と元のファイル名で、Google フォトから探します。
- **撮り方**: 写真はスマホのカメラのアプリで撮り、日記にはアルバムから選んで入れます。ブラウザから直接カメラで撮ると、アルバムに残らず、Google フォトにも上がらないことがあるためです。画面の「写真」のボタンも、アルバムから選ぶ形にします。
- **読み取るもの**: 縮める前の元のファイルから、撮影日時（EXIF の撮影日時）と元のファイル名を読み取って `diary.photos` に残します。端末によっては取れないので（iPhone ではファイル名が `image.jpg` に変わることがある）、実装のときに確かめ、取れなければ空のままにします。
- **消すもの**: 写真の向き（EXIF）は、縮めるときに画素へ反映します。位置情報などの EXIF は、写真にも DB にも残しません。
- **置き場の中**: `<年度>/photos/<ファイル名>`。年度は 4 月始まり。
- **ファイル名**: `<日付>_<その日の通し番号>.jpg`（例: `2026-11-08_01.jpg`）。本文には `![](images/2026-11-08_01.jpg)` と書く。いまの日記の書き方と同じなので、`diary.sections` の `images` の形も変わらない。
- **入れるとき**: スマホでは、写真を縮めて上げるのに数秒かかります。押したことが分かるように、選んですぐ、入れる所に「（写真を上げています…）」の行を置き、上げ終えたら写真に置き換えます。上げているあいだは「写真を入れる」を押せなくし（同じ写真を 2 回入れないため）、進み具合をお知らせに出します。プレビューを開いていれば、上げ終えたときに描き直します。
- **見るとき**: 下絵と同じく期限付きの URL を発行します。
- **使われなくなった写真**: 本文から写真を消して保存したら、どこからも使われなくなった写真を置き場から消します。前の版（`diary.day_history`）に残っている写真は、消さずに残します。

#### 写真のバックアップ

いまのバックアップ（`shared_db_backup`）は、DB を毎日 2 回丸ごと取り、世代ごとに R2 に残しています。Storage のファイル本体は対象外です。写真も同じ形で丸ごと取ると、同じ写真が 30 世代ほど重なって残り、R2 の容量がすぐ埋まります。写真は次のように、別の形で写します。

- 毎日 2 回のバックアップのついでに、`storage.objects` の一覧と R2 の `files/` を比べ、R2 にない写真だけを写します。写真は一度上げたら中身が変わらないので、1 枚につき 1 回写せば足ります。R2 が使う容量は、写真 1 式分で済みます。
- DB と同じく age で暗号化してから送ります。
- 置き場から消えた写真は、R2 では `files-deleted/` に移し、35 日で消します（R2 の lifecycle rule）。消し間違えに気づいたときに戻せるようにするためです。
- 下絵の置き場（`field-plan`）も、同じ形で写します。
- 戻すときは、DB のダンプ（`storage.objects` の行）と `files/` を合わせて戻します。

`shared_db_backup` の側の変更です。日記の画面より先に作ります。日記をこのアプリで書くようになると、写真は Supabase にしか残らないためです。

#### 容量が足りなくなったとき

Storage の 1 GB に近づいたら、そのときに次のどちらかを選びます。

- Supabase を有料のプランに上げる。使い方は何も変わらない。
- 写真を R2 に移し、期限付きの URL を発行する処理（Edge Function）を足す。このときは、使う場所とバックアップがどちらも Cloudflare になるので、バックアップの置き場所を分け直す。

#### 作物と作業の種類

**はじめの形（2026-11-07 から）**

- 保存のときに、節ごとに `diary.tag_words` の語で自動で付けます。付け方は、もとの `build_sections.py` と同じです。
- 画面では、節ごとに作物と作業の種類を札で出し、足したり外したりできます。
- 直した内容は、`diary.days.tags` に、節の見出し（`path`）ごとに持たせます。保存のたびに自動で付け直しますが、直した見出しの節には、直した内容を使います。見出しを書き換えた節は、直した内容が外れて自動に戻ります。

**改める形（2026-11-08 に決めた。まだ作っていない）**

語が含まれていれば付ける形は、決まった語で本文を検索した結果と同じで、検索で足ります。一覧にない作物には付かず、部分一致で違う意味の語にも付きます（「ナス科」でナス、など）。手で直した節も、ほとんどありませんでした。そこで、本文に書いていないことも持たせる形に改めます。細かい計画は、非公開の `inoo_farm` の `docs/diary-tags.md` にあります。

| 項目 | 決めたこと |
|---|---|
| 付ける人 | Claude Code。本人が頼んだときに、本文の意味と写真の中身から付ける。自動では付けず、API も使わない |
| 付ける単位 | 日記の節（見出しごと）と、写真 1 枚ごと |
| 種類 | 作物、作業、場所、症状・病害虫、生育段階、話題 の 6 つと、節の「対象」（その日に実際に使うプランの作付か区画。作付の詳細や日程から、その作付の日記を出すため）。写真には、写っているものと使い道（記事向き・記録向き）も付ける。言葉は DB の一覧から選び、一覧にない語は候補として出して、本人が決めてから足す |
| 言葉の合わせ方 | 作物は品目、作業は記録の作業の種類、場所は圃場と、このアプリの言葉にそろえる |
| 推定と手直し | 手で直した節にだけ印を付ける。それ以外は、すべて推定と解釈する |
| これまでのタグ | 語で自動に付けるタグはやめる。いま付いているタグは、自動のものも手で直したものも消し、まっさらな状態から始める |
| 持ち方 | Claude のタグは `diary.days.ai_tags` に、手で直したタグと同じく見出しごとに持たせる（節は保存のたびに作り直すため）。節には、手直し → Claude の順で選んだタグ（`labels`）と、その出どころを持たせる。写真のタグは `diary.photos` に持たせる |
| 付けるまで | 保存してから Claude が付けるまで、その日の節にはタグがない。探すときは語で探す |

このアプリの側で直したもの（2026-11-08）:

- `field.diary_save_day` が節を作り直すときに、語で付けるのをやめ、手直し → Claude の順でタグを選ぶ。手直しは種類ごとに効き、直していない種類は Claude のタグを使う。
- 節の札を 6 つの種類と対象に広げ、手で直した節にだけ印を付ける。「自動に戻す」は「Claude のタグに戻す」にした。
- 写真のタグは、写真を大きく開いたときに出す。
- 作付の詳細（区画の詳細）の頭に「日記 n 節（最新 M/D）」のボタンを出し、押すと日記の画面で、その対象の札で絞った一覧を古い順に開く（`field.diary_target_sections` で数える）。はじめは作付の詳細の一番下に日記の短い一覧を出していたが、日記の画面の一覧（本文、写真、作業の差し挟み）のほうが中身が多いので、入口だけにした。区画を指す対象で絞ったときは、区画の中の作付を指す節も含める。
- 見出しの名前を変えて保存した節は、手で直したタグも Claude のタグも、新しい見出しに引き継ぐ。保存の前と後で、前にしかない見出しと後にしかない見出しを本文の上から順に組にし、組の数が同じときだけ名前が変わったとみなす（数が違えば引き継がない）。
- 節の分け方を改めた（2026-11-10）: 新しい節を始めるのは、いまの節を始めた見出しと同じか、それより上の段の見出しが来たときだけ。より深い段の見出し（小見出し）は節を分けず、その行も含めていまの節の本文に入れる。`##` と `###` で書けば、`###` は `##` の節に入り、タグは `##` ごとに付く（`###` を一番上に使う日は `###` ごとの節）。小見出しとその下の文や写真は、節を始めた見出しからの深さだけ下げて出す（線や印は付けない）。修正画面に「小見出し」のボタンを足した。これまでの子の節のタグは、親の節に足し合わせて引き継いだ（inoo_farm の `scripts/resplit_sections.py`）。
- 小見出しのあとで親の位置の文に戻る書き方は作らない（2026-11-10）。Markdown には「小見出しを終えて親に戻る」書き方がない。`---`（区切り線）を使う案は、見た目では大きな区切りに見え、見出しの構造を作る道具では直前の小見出しの続きのままなので、どちらの受け取り方とも合わず、やめた。親の位置に書くことは小見出しより前に書き、後に書くことは「### まとめ」のような小見出しにする。
- 空の行を 2 つ以上続けると、増えた分だけ空白の行を出す（Markdown の決まりでは何行でも段落の区切り 1 つだが、書いた見た目に近くする）。
- 節の札を押すと、そのタグの付いた節を並べる。新しい順と古い順を切り替え、札を重ねて絞り、20 節ずつ出す（`field.diary_tag_sections`）。古い順で作物の札を押せば、作物の経過を時系列で追える（作物の経過を出す別の機能は作らない）。
- 対象の札で絞ったときは、その作付（区画）の作業の記録と、まだ終わっていない計画を、日記の節と日付で混ぜて並べる（`field.diary_target_works`）。作業の詳細は作業の記録の側で作り込んであるので、作業の記録に日記を出すのではなく、日記に作業を差し挟む形にした。作業の札を重ねると、作業も同じ種類だけにする（日記の作業の言葉は、記録の作業の種類にそろえてある）。作業の記録を押すと、作業の記録の窓を開く。
- DB を使わないモードも、語では付けず、テストが入れた Claude のタグ（`ai_tags`）と手直しから節のタグを決める。

#### 画面

上のタブに「日記」を足し、「圃場図　日程　品目　日記　履歴」の並びにします。URL は `#diary` です。日記は圃場ごとではなく共通なので、どの圃場を選んでいても、同じ日記を開きます。

**書く（1 日ずつ）**

- 日付を選ぶと、その日の Markdown を開きます。新しい日は空で始まります。
- 入力欄の上に、ボタンを 2 つ置きます。
  - 「見出し」: カーソルの行を見出しにします。
  - 「写真」: アルバムから選び、縮めて上げて、カーソルの位置に差し込みます。何枚か選んだときは、いまの日記と同じく 1 行に並べた表にします。
- 「編集」と「表示」を切り替えて、写真が文中に並んだ形を確かめられます。
- 作物と作業の種類は、表示のほうで節ごとに直します。
- 書きかけの内容は端末の中に残し、電波が途切れても消えないようにします。保存できたら消します。
- 入力欄は、Markdown をそのまま打つ形にします。いまの日記も diary-mcp も Markdown で通っていることと、このアプリはライブラリーを組み込まない形で作っていることからです。

**見る**

- 月のカレンダーを出し、日記のある日に印を付けます。
- 「日」「月」を切り替えると、選んだ期間の日記を、日付の順に続けて並べます（はじめは週もあったが、使わないので外した。2026-11-07）。日を押すと、その日の書く画面を開きます。
- Markdown の表示は、見出し、段落、箇条書き、表、写真を扱います。いまの日記にある、写真を表に並べた形も表示できるようにします。
- 写真を押すと、大きく開きます。撮影日時と元のファイル名が残っていれば、添えて出します（Google フォトで元の写真を探すため）。同じ見出しに写真が 2 枚以上あれば、写真の左右の薄い ‹ ›、← → のキー、スマホでは左右にはらう操作で、同じ見出しの写真を行き来します。端まで行くと反対の端に戻ります（2026-11-09）。

**探す**

- 語を入れると、当たった日の一覧を、新しい日から順に出します。当たった前後の文を添え、語に印を付けます。押すと、その日を開きます。

#### いまの日記の移し替え

`inoo_farm` の変換の途中にできる日ごとの Markdown（`diary/2026/<日付>.md`）には、写真の位置が残っています（`diary.sections` では、写真は本文から抜かれて `images` に移っています）。これを使います。

1. 日ごとの Markdown を `diary.days` に入れるスクリプトを、`inoo_farm` に足して 1 度だけ流します。写真の書き方（`![](images/…)`）は、そのまま使えます。
2. 入れたあと、全部の日を `field.diary_save_day` と同じ手順で節に分け直し、いまの `diary.sections` と同じ行になるかを確かめます。違いがあれば、移し替えの前に、分け方の違いを直します。
3. 写真は、置き場にある元の写真（`<年度>/orig/`）から、新しい形（短辺 1080 px、品質 85）を作って `<年度>/photos/` に置き、`diary.photos` に行を入れます。いまの元の写真は Google ドキュメントの書き出しから取ったもので、撮影日時は残っていないので、撮影日時と元のファイル名は空にします。
4. diary-mcp を新しい置き場に向けたあと、`<年度>/orig/` と `<年度>/small/` を消します。

#### `inoo_farm` の側の変更

- `sql/diary.sql` に、`diary.days`、`diary.day_history`、`diary.tag_words`、`diary.photos` と、写真の置き場の許可を足す。`field` スキーマの関数は、field_plan の `sql/` に置く（`field.is_owner()` を使うため）。
- `load_sections.py` は、日記の節（`diary.sections`）に触れないようにし、LINE だけを入れ直す形にする。いまのままでは、その年度の節をすべて消して入れ直すので、このアプリで書いた日記が消える。
- `import_diary.py`、`build_sections.py`、`upload_photos.py` は、移し替えのあとは使わない。README の「3. 記録を更新するときの手順」から、日記の手順を外す。
- `config/tags.json` を `diary.tag_words` に移し、`import_line.py` が DB から読むようにする。
- diary-mcp の `get_photos` を、`<年度>/photos/` の 1 種類の写真を読むように直す。Claude に見せる画像も、開くためのリンクも、同じ写真を使う。`diary.photos` の撮影日時と元のファイル名も返し、サーバーの説明に「SNS 用にもっと大きい写真が要るときは、撮影日時と元のファイル名で Google フォトから探す」と書き足す。
- README の「日記を守る仕組み」と「3. 記録を更新するときの手順」を、新しい形に合わせて書き直す。

#### テスト

テストには、作った文章と写真だけを使います。本物の日記の文や写真は、テストにも画面の見本にも使いません。確かめること:

- 節の分け方が `build_sections.py` と同じになる（見出しの階層、写真の抜き出し、空の節の扱い）。
- 直した作物と作業の種類が、保存し直しても残り、見出しを変えた節では自動に戻る（タグを改めたあとは、自動ではなく Claude のタグに戻る）。
- 本人でないログインでは、関数が何も返さず、写真の置き場も読めない。
- 写真を消して保存すると、使われなくなった写真だけが置き場から消える。
- 写真の縮め方: 縦向きでも横向きでも短辺が 1080 px になり、元が小さいときは広げない。向きが画素に反映され、位置情報が残らない。撮影日時が取れないファイルでも上げられる。

### 11.2 農作業日記との突き合わせ

日記（`inoo_farm` の `diary` スキーマ）にあるのは、日付、作物、作業の種類、本文、写真です。区画や畝の情報はないので、日記から「どの畝の作業を、いつ行ったか」を自動で決めることはできません。記録はこのアプリで入れ、日記は裏付けと詳細として、記録の横に出す形を考えています。

- **対応の表**: 作業の種類と品目を、日記の作業の種類と作物に対応させます。

  | 作業の種類 | 日記の作業の種類 |
  |---|---|
  | 畝立て | 畝立て・耕うん |
  | ロータリー、すき込み | 畝立て・耕うん |
  | マルチ張り | マルチ |
  | 育苗の播種、定植・播種 | 定植、播種 |
  | 堆肥・石灰・基肥、追肥 | 施肥 |
  | 防除 | 農薬散布（日記の側の名前） |
  | 収穫 | 収穫、出荷 |
  | 残渣処理 | 片付け |
  | 心土破砕、太陽熱消毒、緑肥、灌水、発芽確認、除草、資材の設置 | 対応する種類なし（日付だけで探す） |

- **記録の横に日記を出す**: 記録の日（記録がなければ計画の日）の前後数日で、作業の種類と作物が合う日記の節を一覧にします。
- **日記から記録を作る補助**: 合う日記があり、記録のない計画の作業には、「この日記の日付で記録を作る」を出します。押したときだけ作ります。
- **日記を読む仕組み**: 11.1 の `field.diary_get_days` を使います。日記の節だけを返し、LINE のメッセージは返しません。

取り組むときに決めること:

- この圃場の作業も、同じ日記に書くか。書くなら、見出しに区画や畝の名前を入れると、突き合わせの精度が上がる。
- 日記の側の「農薬散布」を「防除」に改めるか。心土破砕、太陽熱消毒、緑肥、残渣処理、灌水、除草などを、日記の側の作業の種類にも足すか。どちらも `inoo_farm` の `config/tags.json` を変える。

### 11.3 記録の写真

2026-11-09 に決めた: **写真は日記に付け、作業の記録（メモ欄）には付けない。** 作業と写真は、日記の対象の一覧で並べて見る。

はじめは、記録に写真を付けるなら、その日の日記に入れた写真から選んで記録につなぐ形を考えていた。日記のタグの一覧で、対象の札（作付か区画）で絞ると、その作付の作業の記録と予定が日記の節と日付の順に並ぶようになった（11.1）。作業のすぐ近くに、その日の日記の写真が出るので、記録に写真を持たせなくても、作業と写真を一緒に見られる。

記録に写真を付けない理由:

- **写真の置き場を 1 つにする**: 日記の写真には、すでに次のものがそろっている。記録にも写真を持たせると、これを二重に作るか、記録の写真だけ使えない状態になる。
  - 1 種類の大きさ（短辺 1080 px）
  - Google フォトで元を探す手がかり（撮影日時と元のファイル名）
  - 写真のタグ（写っているもの、記事向き・記録向き）
  - R2 への差分のバックアップ
  - diary-mcp の `search_photos` と `get_photos`（記事の写真選び）
- **どこに付けたかで迷わない**: 写真を 2 か所に付けられると、あとで探すときに両方を見ることになる。
- **記録は決まった形のまま保つ**: 記録は、仕様・資材・量など、集計に使う情報。メモ欄は補足にとどめる。

気を付けること:

- 日記の写真が作業の隣に並ぶのは、Claude Code が日記に対象のタグを付けたあと。書いた直後は、まだつながっていない。日記の見出しに、作付の名前（「区画1 畝10 島にんじん」など）を書いておくと、対象を付けやすい。

#### これから作るもの: 作業の記録の窓の「保存して日記を書く」

畑で作業を入れたあと、写真や様子を書くために日記へ移る手間を減らす。作業の記録の窓に「保存して日記を書く」のボタンを置く。

- **押したとき**: 作業の記録を保存してから、その日の日記の修正画面を開く。保存してから開くのは、書きかけの記録を失わないため。保存に失敗したときは、日記を開かない。
- **開く日**: 記録の日付（何日かにわたる作業は、始めた日）。
- **見出しを入れる**: 本文の最後に、作業の対象の見出しを入れ、カーソルをその下に置く。日記に写真を入れるのは、そのあと「写真を入れる」で行う。
  - 対象が作付 1 つなら、その表示名（「区画1 畝10 島にんじん」）。
  - 同じ品目の作付が複数なら、区画と品目（「区画2 大根」）。品目が混ざるときは区画の名前。
  - 区画の作業なら、区画の名前。
  - その日の本文に同じ見出しがもうあれば、新しく足さず、その見出しの下にカーソルを置く。
- **書きかけの日記がほかの日にあるとき**: いまの日記の画面と同じく、「書きかけの日記があります。保存するか、やめてから開いてください」と出して、開かない（記録は保存したまま）。
- **日記を保存したあと**: 日記の画面のまま。作業の記録の窓には戻らない。
- **見出しの効き目**: 見出しに作付の名前が入るので、Claude Code がタグを付けるときに、対象（作付か区画）を付けやすくなる。

Google フォトに置いたまま、このアプリから見る形は採りません。2025 年 3 月から、外部のアプリは Google フォトにもともとある写真を読めなくなり、選んで受け取った写真の URL も 60 分ほどで切れるためです。
