# 速さの確かめ方

画面の速さは、データが増えるほど、気づかないうちに落ちていく。そこで、決まった時期に測って前回と比べ、悪くなっていたら、くわしく調べて直す。

## 続け方

1. **定期の確かめ（1 月と 7 月）**: 1 日に、GitHub Actions（`.github/workflows/perf-check.yml`）が「定期の確かめ: 速さ」の Issue を開く。Issue の手順に沿って測り、結果を `docs/perf-runs.md` に足して閉じる。10 分ほどで済む。
2. **レビュー**: 下の「レビューに進む目安」に当たったら、本物のデータで、どこが遅いかを調べる。本物のデータの件数や中身は、このリポジトリには書かず、非公開の場所の文書にまとめる。
3. **直す**: 直す候補は、1 つずつ Issue にし、`performance` のラベルを付ける。Issue には、圃場の内容を書かず、直す所と理由だけを書く。

定期の確かめを待たずに、次のときもレビューする。

- 新しいタブや表を足すなど、大きな機能を足したとき
- 本番のデータの件数（作業、作業の記録、変更の記録）が、前のレビューのときの 2 倍ほどになったとき
- 使っていて遅いと感じたとき

## 測り方

```
node scripts/perf/run.mjs            # いまの量と 1 年後の量を測って、結果を出す
node scripts/perf/run.mjs --record   # 結果を docs/perf-runs.md の表に足す
```

- 作り物のデータ（`scripts/perf/data.mjs`）を `?local=1` の画面に入れ、Chrome で測る。本物のデータは使わない。
- 測るのは、起動（開き直して画面が出るまで）、タブの切り替え（押してから次の描画まで）、そのあいだの配置の計算の回数、起動の読み込み（`field.load_field`）が返す中身の大きさの見込み。
- 「スマホ相当」は、PC の CPU を 1/4 に絞り、幅を 390 px にした値で、実機の値ではない。
- 値は、測るたびに 1〜2 割揺れる。PC が忙しいと 2 倍ほど揺れる。ほかの重い処理を止めてから測り、前回と大きく違えば測り直す。
- 通信の時間は含まない（`?local=1` は DB を使わない）。起動の読み込みの通信は、中身の大きさの見込みで見る。

### 測るデータ

| データ | 中身 |
|---|---|
| いまの量 | 2026-11 の本番とほぼ同じ件数。畝 104 本、作付 104、作業 約 430、作業の記録 110、変更の記録 540 |
| 1 年後の量 | 1 年使ったときの見込み。作付 208、作業 約 850、作業の記録 1,300、変更の記録 5,000 |

本番の件数が「1 年後の量」に近づいたら、`data.mjs` に、さらに先の量を足す。

### 実機での確かめ

定期の確かめでは、iPhone（Safari）でも、起動とタブの切り替え（日程、圃場図、台帳、履歴）を試し、もたつきを感じるかを書き残す。数値は取らない。

### 実機の起動のログ

作り物のデータの測定は、通信の時間を含まない。実機の起動で、どの通信をどれだけ待っているかは、Android の Chrome のネットワークの記録で見る。

1. スマホの Chrome で `chrome://net-export` を開き、記録を始める（Include cookies and credentials は選ばない）。
2. 別のタブでアプリを開き、画面が出るまで待つ。
3. 記録を止め、できたファイル（JSON）を PC の `data/起動ログ/` に置く。`data/` は `.gitignore` で除いてあり、リポジトリには入らない。
4. ファイルは大きいので、要求ごとに、始めた時刻・待った時間・ネットワークに出たか・大きさを集計して読む。結果は `docs/perf-runs.md` の「実機の起動」の表に足す。

いちばん遅くなりやすいのは、しばらく使っていなかったあとの最初の起動（ログインの更新が要り、事前確認も切れている）。比べるときは、条件をそろえる。

## レビューに進む目安

次のどれかに当たったら、レビューに進む。

- 「いまの量」の値が、前回の記録の 1.5 倍を超えた（測り直しても同じとき）
- 「いまの量」で、タブの切り替えが 500 ms、起動が 1,500 ms を超えた
- 「1 年後の量」で、タブの切り替えが 1,000 ms、起動が 3,000 ms を超えた
- 起動の読み込みの中身が、「いまの量」で 1 MB を超えた
- 実機で、もたつきを感じた

## 見えている課題

- 起動の読み込み（`field.load_field`）は、圃場の作業の記録を全件返す。「1 年後の量」では約 2 MB になる。DB が変わっていなければ受け取らずに済むが（端末に取っておいた中身を使う）、自分で記録を入れた次の起動では、毎回受け取る（Issue #6）。
- 起動の時間と、日程・圃場図への切り替えは、作業と作付の数に比例して重くなる（2026-11-15 の記録で、1 年後の量はいまの量の 1.5〜2 倍）。
- 実機の起動（2026-11-16 のログ）では、画面が出るまでの待ちの大部分が、アプリの外にある。
  - ログインの更新：0.8〜1.2 秒。回線が悪い日は、これだけで 8.7 秒かかったことがある。
  - PostgREST の最初の返事：DB の中の処理は 11 ms だが、しばらくあけたあとの最初の要求は、約 0.6 秒余分にかかる。PostgREST は、30 秒ほど使われない DB とのつながりを閉じるので、つなぎ直しが起きる。
  - 要求の数と受け取る量は、まとめた読み込みと、端末に取っておいた中身で、ほぼなくなった。
- アプリの更新の確かめは、起動のたびにファイル約 45 個をサーバーに確かめていて、始まるのも画面が出たあとになる（Issue #7）。

## 試していること

- **ログインの更新と並べて、agri_db の公開の読み取りで PostgREST を先に起こす**（2026-11-16 から。`app/app.js` の `warmPostgrest`）
  - agri_db は、同じ Supabase のプロジェクトの `public` スキーマで、ログインなしで市況の集計を読める。PostgREST はプロジェクトに 1 つで、DB とのつながりを、スキーマや利用者の別なく使い回す。そのため、これを 1 行読めば、そのあとの `load_field` は、つなぎ直しを待たずに済むはず。
  - 送るのは、ログインの鍵の期限が切れていて、ログインの更新を待つときだけ。field スキーマへの扉は開けない。公開キーを URL に入れ、見出しを付けないので、事前確認も付かない。返事は読まない。
  - **確かめ方**：実機の起動のログ（しばらくあけたあとの起動）で、`load_field` の本体の「送ってから返事の頭まで」を見る。2026-11-16 の改善の前は 0.79 秒（事前確認の往復は 0.16 秒）。
  - **外す目安**：何日か取って、縮んでいなければ外す。agri_db の表の名前を変えたときも、ここを直すか外す。

## 検討して見送ったこと

- **ログインなしで呼べる DB の関数を field スキーマに作り、ログインの更新と並べて呼んで、PostgREST を先に温める**（2026-11-16）。「ログインのない利用者は `field` スキーマに触れない」という守りの形を崩すので、とらない。同じプロジェクトの agri_db の公開の読み取りで代わりになることが分かったので、そちらを試している（上の「試していること」）。わざと断られる要求を送って温める形も考えたが、仕組みの細かい振る舞いに頼る小技なので、とらない。
- **ログインの鍵の期限（1 時間）を延ばして、朝のログインの更新をなくす**。ログインを取り消したり、パスワードを変えたりしても、鍵の期限まで使えてしまうので、とらない。
- **DB の中から自分を定期的に呼んで、PostgREST のつながりを温めておく**。一日中、要求を送り続けることになり、ログインの更新の遅さにも効かないので、とらない。
