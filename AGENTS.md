# Implementation rules

Rules to follow when writing or changing code. The rules for how screens look are in `docs/design-rules.md` (Japanese). Before a commit, `jev-lint` checks each change against this file (README section 12).

## Waiting

- **When a function waits for a confirmation dialog or a save, its callers also `await` it.** `confirmAction` and `confirmDelete` do not finish until the user answers. Code after the call runs before the answer unless it waits.
- **When you change a synchronous function to async, fix every caller.** If the called function does not return the Promise, nothing after it can wait. A function that only wraps another one must also `return` it.
- **Redraw the map only after the data has finished changing.** `render` draws only the field map and the right-hand panel. When you change the schedule screen, also call `renderSchedule`.

## Order of saves

- **Send a parent row before its child rows.** Foreign keys run zone → block → bed → planting → work, and a child that arrives first is rejected with 23503. It does not happen every time, so trying the screen is not enough to notice it.
- **Write to the database only through `state.store`.** `inOrder` sends writes one at a time in the order they were called, so calling the parent first keeps the order.
- **`queueSave` does not send right away.** It sends 600 ms later. Before saving a row whose parent was passed to `queueSave`, wait for `sendPendingSaves`.
- **A value that changed on screen does not mean the save has finished.** Anything that follows a save waits for it to complete.
- **When you add a database write function, also add it to `QUEUED_WRITES`.** That list decides the order of sending and the operation ID (`op_id`).

## Reporting failures

- **Report a failed save in a dialog.** The notice under the header is replaced or cleared when another save finishes. `persist` and `run` call `notifySaveFailed` on failure, so save through them.
- **Show save status text with `setStatus`.** While anything is left unsent, do not write 「保存しました」; send it again. The text goes into the invisible log field (`#saveStatus`), and `app/toast.js` shows it as the notice under the header. Write a failure as 「…に失敗しました: 誤りの内容」 or 「…ませんでした: 誤りの内容」 (only text in this form becomes a notice that stays until it is closed).
- **Do not swallow failures.** After a `catch`, tell the user in a way they can see.

## Undo

- **Undo works by the operation ID of the writes.** `history.js` records the operation ID current when a write enters the queue (the writes are `upsert`, `remove`, `saveField`, `saveLog`, `deleteLog`, `saveWorkType`, `saveBackdrop` and `saveFieldWeather` in `store.js`, and the plan operations `createPlan`, `copyPlan`, `renamePlan`, `deletePlan` and `setActivePlan`; the list is `UNDOABLE_WRITES` in `history.js`). The database function `field.undo_op` reverts that ID's changes on the database side, and the returned rows are applied to the screen (`applyUndo` in `app.js`). A new operation that goes through these writes needs no undo code of its own.
- **Send writes inside the operation.** The operation ID is created at the start of a click or key press. If a write comes after an `await` following the click, the next operation may start in between, and the write is recorded under the other operation's ID. Scheduled saves (`queueSave`) and the write queue (`inOrder`) send with the ID current when they were scheduled, so use them.
- **When you add a table, check the four places Undo depends on.** `tests/undo-tables.test.mjs` finds a table missing from places 1 to 3. Place 4 is not covered by tests.
  1. The table order in `field.undo_op` (`v_order`, parents before children).
  2. `UNDO_APPLY` in `history.js` (how rows are applied to the screen; `UNDO_NOT_APPLIED` if none is decided) and `applyUndo` in `app.js`. When `applyUndo` gets rows of a table it cannot apply, it reloads from the database and clears the history.
  3. The change log of the browser store (`AUDITED` in `store.js`).
  4. Selecting and highlighting the reverted rows (`showUndone` in `app.js`). It finds rows by `data-` attributes of screen elements (`data-shape`, `data-bed`, `data-planting`, `data-id` of `.gantt-bar` and `.pe-card`, `data-plan` of `td.detail-plan`, `data-log` and so on), so when you add a table or a screen that shows rows, add it here too.
- **After an operation that cannot be undone, call `resetHistory()`.** Writes after that are not recorded under that operation's ID.
- **Make an operation that does not depend on the plan a field operation.** Each history entry remembers the plan that was open when it was made, and is not reverted while another plan is open. Plan operations (`createPlan` and so on) become field operations automatically. For a field operation written in several steps (saving the field settings dialog), call `markSettingsOperation()` before writing, and bind the writes to the same operation ID with `bindOperation`. Plan operations and field settings saves open their dialog before undo and redo revert them (`ctx.showDialog`).
- **When you add an operation that writes to the database from a dialog, decide whether undo reopens that dialog.** Each history entry remembers the screen (the URL hash) where the operation happened, and undo and redo move to that screen. Dialogs do not change the URL, so usually this only moves to the screen behind the dialog. Only the 「圃場とプラン」 dialog and the field settings dialog are reopened now (`dialog` in `history.js`, `showDialog` in `app.js`).
- **List operations that cannot be undone in the README section 「元に戻す、やり直す」.**

## Changing the database schema, adding parts

The app keeps all its files in the browser (`app/sw.js`) and starts from them. It switches to a new version when the user presses 「読み込み直す」 in the notice, or the next time it opens. So for a while after a release, screens of the old version still write to the database.

- **When you change the database in a way old screens cannot write correctly, stop the old version.** For example when you rename a column, add a required column, or change a write rule. Do it in this order:
  1. Raise `APP_VERSION` in `app/store.js` by one and publish the screens that match the database change.
  2. Close screens that are still open. The version is checked only at startup, so open screens do not stop.
  3. After the release is out, in the SQL that changes the database, raise `min_version` in `field.app_compat` to the same value (`update field.app_compat set min_version = 2;`).

  A screen older than `min_version` stops at startup before showing data, and reloads the new version. In the reverse order it stays stopped, because the new version does not exist yet.
- **If a change can keep old screens working, make it that way.** Adding a column alone lets the old version run without knowing the new column. Add the new column first, make both versions work, then remove the old column.
- **When you add a table to the `field` schema, add it to the policy list in `sql/field.sql`.** `field.sql` first lets `authenticated` read and write every table, then puts policies on the tables in the list. A table missing from the list gets only RLS, nobody can read or write it, and the final check in `field.sql` fails. Add a table the screens never read or write to the check's list of tables that need no policy.
- **When a policy condition calls `field.is_owner()` or `field.is_importer()`, wrap it in `select`, like `(select field.is_owner())`.** Without it the function runs for every row read. With it the function is evaluated once per query (measured on 2026-11-15: reading 450 work rows went from 6.7 ms to 0.4 ms). An unwrapped policy makes the final check in `field.sql` fail.
- **When you add a table to the `field` schema, decide whether it goes into the operation log (`audit_log`), and add it to one of the two lists in `sql/field.sql`.** Tables the screens read and write and whose changes from other devices must be picked up, such as plans and records, go into the list that gets the trigger (`write_audit_log`). Admin tables and tables imported from outside go into the final check's list of excluded tables. A table in neither list makes the final check in `field.sql` fail.
- **What is read at startup, on return to the app and on switching fields is decided in two places: the database function `field.load_field` (`sql/field.sql`) and `composeLoadField` in `app/store.js`. When you add a table, or change how rows are filtered or ordered, change both.** Tables are returned as whole rows, so adding a column alone needs no change. `composeLoadField` is used by the `?local=1` store and when the database function is missing.
  - `tests/load-field.test.mjs` checks that the two places read the same tables. When you add a read to `composeLoadField`, add it to `LOADERS` in the test too.
  - Tables read there go into `audit_log`. The screen does not reload when the database change mark (the last number of `audit_log`) is the same as last time. Changes to a table without the trigger do not advance the number, so changes from other devices are not picked up. `tests/audit.test.mjs` checks this.
  - The end-to-end tests only go through `composeLoadField`. When you change `load_field`, connect to the production database directly, call it with the owner's rights, and check that it returns the same result as reading each table (including the order).
- **The field data kept on the device (`app/field-cache.js`) is only what was read from the database as is, plus the database change mark of that moment. Do not keep the screen's `state`.** At startup, when the mark is the same, the kept data is used as the database data. Keeping data that was changed on screen but could not be saved would show it as database data. What is kept is the reply of `store.loadField`, copied at the moment it is called (`writeFieldCache`). When you change the kept format, raise `FORMAT`. Data from another app version (`APP_VERSION`) is not used. The diary is not kept. It is cleared on logout.
- **Do not change data copied from the database (the tables in `state`) without sending a write.** The reload on return does not compare with the database when no write came from anywhere. A screen-only change without a write stays out of sync. When a write fails, `inOrder` counts the failure and the app reloads on the next return.
- **When you add a JS module (file), add it to both `FILES` in `app/sw.js` and `parts` in `app/boot.js`.** A missing one is left out of the file set, and old and new versions get mixed. `tests/sw.test.mjs` checks for omissions.
- **The version mark (`app/version.json`) is made by the release step (`scripts/build-version.mjs`) from the files being published. Do not make it by hand. Do not commit it (it is in `.gitignore`).** It follows changes to `FILES` automatically. The Service Worker uses the version mark to tell whether the version changed, and checks the fetched files against the hashes in it before switching (so a mix of old and new files arriving right after a release never runs as a set). After a release, Actions checks that the published site matches the version mark.
- **When you add a file the screens load (icons and so on), also add it to `FILES`.**
- **Put scripts in files, never inside HTML.** The Content-Security-Policy of `index.html` runs only scripts from this site's files. Code inside `<script>`, attributes such as `onclick`, and `javascript:` links do not run. `tests/sw.test.mjs` checks this.
- **Pass every piece of text that goes into HTML through `escapeHtml` from `app/html.js`.** Do not write a copy of it per module (there were once 17 copies, and one of them differed).
- **Write `sql/field.sql` so that it runs to the end on an empty database.** Do not alter a table before it is created. A `language sql` function checks its body when it is created, so put it after the columns it uses are added. After a change, check it with `scripts/check_field_sql.py` (README section 12).
- **Never load scripts from outside servers.** Put an external library as a fixed-version file in `app/vendor/` and add it to `FILES`. Loading from outside changes the content without an app change, leaves it out of the file set, and keeps the app from starting when it cannot be reached. `tests/sw.test.mjs` checks this. How to upgrade it is in README section 12.

## Drawing screens

A screen is drawn by rebuilding the content of a container from an HTML string. Rebuilding loses the scroll position and the cursor, so draw through `draw` in `app/draw.js`. Before rebuilding, `draw` remembers the height of the area being touched, the scroll positions and the field with the cursor, and restores them afterwards.

If `draw` is later replaced by something that rewrites only the differences (idiomorph and the like), only the inside of `draw` changes. It will then keep the previous elements instead of rebuilding. Follow these rules so that nothing else has to change at that point.

- **To replace content, use `draw(container, html)`. Do not use `innerHTML`, `outerHTML` or `insertAdjacentHTML` directly.** Using them directly loses the scroll position and the cursor. `tests/draw.test.mjs` checks this. To only empty a container, `replaceChildren()` is fine.
- **Keep screen state in data. Do not read it back from drawn elements.** Checks, selections, open panels and half-typed text go into data (`draft` and so on) on every operation, and drawing builds the HTML from the data. State left in elements disappears when they are rebuilt, and with a scheme that keeps previous elements the old value stays. Both look the same only when drawing from data.
- **Set state that HTML cannot express (`indeterminate` and so on) from the data on every draw.** Set it right after `draw`. Do not rely on a value set earlier still being there.
- **Attach event handlers to the container or an element outside it, never to elements of the drawn content.** On content elements they disappear on every draw when rebuilding, and pile up on every draw with a scheme that keeps previous elements. Attach to the container and tell which element with `event.target.closest(…)` (`bind` in `crops-view.js`).
- **Do not hold on to drawn content elements past a redraw.** After a redraw, find them again with `querySelector`. Rebuilding detaches the previous elements, and with a scheme that keeps previous elements the same element holds different content.
- **Mark inputs, buttons and rows with `data-*` or `id` so each can be identified.** `draw` uses these marks to find the same element after rebuilding (it combines a row's `data-id` with a field's `data-field` to tell which field of which row). The cursor cannot be restored into an unmarked element. A scheme that rewrites only differences also matches elements by these marks.
- **Do not skip drawing a panel because of which screen is showing.** Dialogs open from every screen. The weather panel of the field settings dialog skipped drawing while the field map was hidden, so opening the dialog from the schedule screen showed the panel from startup (2026-11-17). Skip only when the data needed to draw is not there yet (before the field is loaded, for example).
- **Do not rely on a rebuild to reset anything.** Clearing half-typed text, scrolling back to the top and similar resets need their own code. A scheme that keeps previous elements does not rebuild, so nothing resets. This is also why the dialog empties its content after closing (`log-view.js`).
- **When JS changes a scroll position (`scrollTop`, `scrollLeft`), call `noteScroll(element)` from `draw.js`.** Before redrawing, `draw` remembers and restores the positions of scrolled elements. Which elements are scrolled is learned from scroll events. Reading the position of every element on every draw would make the browser recompute the whole page layout each time, which is slow (the schedule chart has thousands of elements), so it does not do that. Scroll events arrive a little late, so a redraw in the same task right after changing the position loses that position unless `noteScroll` is called.
- **Do not add code that reads element sizes or positions inside `draw`.** It would force a layout of the whole page on every redraw. Anything that must be read before drawing is read by the caller, in one batch, so the number of reads does not grow.
- **Do not redraw the container of a field on every keystroke (`input` event).** Rebuilding in the middle of Japanese input conversion breaks the conversion. Put what changes on every keystroke (search results and so on) in a separate container, and draw only that.

- **To make part of an SVG text clickable, do not split it into `tspan`; find the character from the clicked position.** In WebKit (Safari and Chrome on iPad and iPhone), splitting into `tspan` makes `dominant-baseline` stop working so that part shifts vertically, and `pointer-events` stops working so the shape underneath gets the click. Neither happens in Chrome on a PC, so the end-to-end tests cannot notice. The crop names on the field map keep the text as one piece and use `getExtentOfChar` to tell whether the clicked position falls on the crop name (`mapLabelAt` in `app.js`). When the text overflows its shape, draw the text after all shapes (drawn earlier, it hides behind the neighbouring shape).

## Checks

- **When you change the flow of operations, run the browser end-to-end tests.** The calculation tests cannot find bugs in screen operations. When you add a main operation, add a test to `tests/e2e/`.
- **Do network work on returning to the app through the `app-returned` event.** `app.js` fires it only when the app returns after being hidden for 60 seconds or more (reloading the field data, reloading the news, checking for app updates). Listening to `visibilitychange` yourself and going to the network wakes the phone's radio every time the user switches apps for a few seconds.
- **When you add a large feature, measure screen speed with `node scripts/perf/run.mjs` and compare with the last record in `docs/perf-runs.md`.** How to continue, and when to go on to a review, are in `docs/performance.md`. In January and July, Actions opens the periodic check issue.
- **When you change a calculation file, check before the commit with `node mutation/run.mjs --since HEAD` that the calculation tests notice errors.** The targets are the files in `include` of `mutation/mutator.config.json`, and only the uncommitted changes are run. If a Survived mutant appears where you changed code, add a test; if NoCoverage appears, add a test that reaches that place. A mutant that gives the same result however it is rewritten is recorded with `node mutation/run.mjs accept <key> --reason "reason"` and committed (do not record one you cannot show to be equivalent). Functions involved in pesticide use counts, standards, amounts and warnings carry `// mutator-critical`; do not commit while mutator exits with code 2 (an undetected mutant in such a function that is not recorded). The same applies when you fix a calculation bug and add a test. When you upgrade mutator, and in the January and July checks, run the whole set and add it to `docs/mutation-runs.md` (README section 12).
- **Run changes that involve saving with `?local=1&strict=1`.** It slows the saves of parent tables and rejects rows without a parent. Plain `?local=1` finishes saves at once, so ordering mistakes do not show.
