# field_plan

[![版](https://img.shields.io/badge/dynamic/json?url=https%3A%2F%2Fyonhon.github.io%2Ffield_plan%2Fversion.json&query=%24.label&label=%E7%89%88&color=4c9a2a)](https://yonhon.github.io/field_plan/)

いのーファームの圃場の計画と管理を、ブラウザーで行うアプリです。
計画は PC で作り、作業内容はスマホで確認します。見られるのはログインした本人だけです。

## 考え方

計画は、実際の作業の順に、次の 4 つの入れ物で持ちます。

| 入れ物 | 内容 |
|---|---|
| 有効圃場 | 耕してよい場所。物置、井戸、通路を除いた範囲 |
| 耕起対象区画 | 有効圃場を線で分けたもの。**畝立ての前まで**の作業（心土破砕、ロータリー、太陽熱消毒、緑肥など）を区画ごとに計画する |
| 畝 | 区画の中に置く四角形。前後と左右の隙間が通路になる |
| 作付 | 1 本の畝で、**畝立てから収穫まで**の 1 回ぶん。品目と作業（畝立て、マルチ張り、定植・播種、収穫、残渣処理）を持つ |

時間の決まりは次のとおりです。

- 畝には、前の作付の収穫完了予定日のあとに、次の作付を置けます。回転の速い品目は、同じ畝に作付が 2 つ、3 つと並びます。
- 収穫完了予定日より後の日付で、畝をなくせます。
- 畝のない場所は、その日付から新しい耕起対象区画に設定し直せます。前の日付を表示すれば、前の区画と畝が見えます。

### 作る順番

1. 圃場と区域の作図（済み）
2. 耕起対象区画、畝、作付と、その作業の計画（済み）
3. 日程の逆算と警告（済み）
4. 品目の設定値からの苗数、施肥量の計算（済み）
5. 作業の実績（実績と管理作業の計画の入力、計画とのつながりまで作った。[計画](docs/actuals-plan.md)）

### 計算式

| 項目 | 式 |
|---|---|
| 苗数 | 切り捨て（畝長 ÷ 株間）× 条数 |
| 畝の面積 | 畝長 × 畝幅 |
| 窒素量 | 畝の面積 × 10 a あたりの窒素量 ÷ 1,000 ㎡ |
| 肥料の量 | 窒素量 ÷ 肥料の窒素成分（%） |

## 構成

`agri_db`、`inoo_farm` と同じく、ビルドのない静的な HTML/JS と Supabase で作ります。
Supabase のプロジェクトは共用で（プロジェクト参照 ID: `byhthaiwbutqstrqbwwc`）、このアプリのテーブルは `field` スキーマに置きます。

| 場所 | 内容 |
|---|---|
| `app/` | 画面。GitHub Pages に置く。外のライブラリー（supabase-js）は `app/vendor/` に版を決めて置く |
| `sql/` | `field` スキーマのテーブル、関数、権限（`field.sql`）と、農作業日記を画面から読み書きする関数（`diary.sql`。日記のテーブルは `inoo_farm` の `diary` スキーマ） |
| `supabase/functions/` | Supabase Edge Function。MCP サーバー（`field-mcp`）、2 週間気温予報（`field-weather`）、Google フォトの写真の中継（`field-photos`） |
| `scripts/` | DB への取り込み（FAMIC、RAC コード、気象、県のニュース）、本番への作業の記録の投入（`save_logs.py`）、公開の版の印と MCP サーバーへの部品の写し、確かめの道具（空の DB での SQL、画面の速さ、StrykerJS） |
| `.github/workflows/` | 公開と配備、取り込みの定期実行、半年ごとの確かめの Issue |
| `tests/`、`tests/e2e/` | 計算と MCP サーバーのテストと、Chrome で通して動かすテスト |
| `mutation/` | Mutation testing（mizchi/mutator）の道具と設定 |
| `docs/` | 使い方、開発の手順、計画、確かめの記録 |
| `data/` | 下絵の画像など、圃場ごとの資料。**Git の対象外** |

それぞれのファイルが何をするかは、ファイルの先頭のコメントに書いています。
テーブルの形と、画面の部分がどのファイルにあるかは、[開発の手順](docs/development.md)にあります。

画面のコードは公開されますが、データはログインした本人しか読めません。

## データを守る仕組み

- テーブルは `field` スキーマに置き、RLS で `field.owners` に登録した利用者にだけ読み書きを許します。`sql/field.sql` は、すべての表に RLS を付け、最後に、RLS のない表と、許す相手を決めていない表がないことを確かめます。
- 画面は、このサイトのスクリプトだけを動かします（`index.html` の Content-Security-Policy）。HTML の中に書いたスクリプトや、押すと動くリンク（`javascript:`）は動きません。画面は HTML の文字列を組み立てて描くので、文字の置き換え（`app/html.js` の `escapeHtml`）を 1 か所忘れても、そこからスクリプトを動かせないようにするためです。ニュースのリンクは、`http` と `https` だけをリンクにします。
- 写真の中継の関数（`field-photos`）も、`field.owners` にいる利用者だけが呼べ、読みに行く先は Google フォトの写真の置き場（`lh*.googleusercontent.com`）に限ります。写真は中継するだけで残しません。
- 2 週間気温予報の関数（`field-weather`）は、`field.owners` にいる利用者だけが呼べます。関数の中で、送られてきたログインの印を DB に尋ねて確かめます。
- 利用者の登録は、Supabase の設定で止めています（Authentication > Sign In / Providers の「Allow new users to sign up」）。公開キーを知っていても、利用者は作れません。利用者を足すときは、管理画面の Authentication > Users で作ります。
- 下絵の画像（集成図など）には地番や氏名が写っていることがあるので、リポジトリに入れず、非公開のストレージ（`field-plan`）に置きます。
- 農作業日記には、ほかの方の氏名や連絡先が入ります。日記は `inoo_farm` の `diary` スキーマにあり、API には出していません。画面は `sql/diary.sql` の関数だけを通して読み書きし、関数は `field.owners` に登録した本人でなければ止まります。写真は非公開のストレージ（`diary-photos`）に置きます。本物の日記は、テストにも画面の見本にも使いません。
- 圃場の場所、面積、作付の予定などは、このリポジトリに書きません。DB にだけ置きます。
- 計画の表の行を足す・変える・消すたびに、DB が変える前と後の行を `field.audit_log` に残します。DB が一緒に消した行（区画を消したときの畝など）も残ります。画面からは読めず、事故を調べたり、消えた行を戻したりするときに、DB に直接つないで読みます。1 年より古い行は、毎日 3:30 に pg_cron が消します。開発日誌のための変更の記録（`field.changes`）とは別のものです。
- 共用の DB 全体を、毎日 2 回（16:23 と 4:23 が目安）バックアップします。暗号化してから Supabase の外の非公開の置き場に送り、直近 8 日、週ごと 35 日、月ごと 370 日のぶんを残します。仕組みと戻し方は、非公開のリポジトリ `shared_db_backup` にあります。下絵の画像と日記の写真は、DB とは別に、新しいものだけを暗号化して同じ置き場に写します。消えた行を戻すときは、まず `field.audit_log` を見て、それで戻せないときにバックアップを使います。
